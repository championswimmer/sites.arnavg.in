Designing pi-extension-settings-dialog

A feasibility study and technical blueprint for a zero-dependency wrapper over @earendil-works/pi-tui that gives any Pi extension declarative settings schemas, Global vs Project layered JSON persistence, Ctrl+S draft workflows, and native mouse support in fullscreen TUI mode.

Feasibility Verdict
Strong yes — high leverage

4 real Pi extensions re-implemented 2,000+ LOC of overlay framing, route stacks, and JSON hardening with inconsistent UX and safety.

Why pi-tui Isn't Enough
SettingsList is too flat

Built-in SettingsList handles flat cycling and one submenu slot, but lacks text/number editing, validation, tabs, drafts, and provenance.

Mouse in Full TUI
Ready in Pi v1.5.2

TuiAltScreen already dispatches overlay-local TuiMouseEvents with click synthesis and wheel deltas; only 1 of 4 extensions uses it.

01 / Executive Verdict

There is a clear, well-bounded library waiting to be extracted

Inspecting four production Pi extensions (pi-context-decisions, pi-subagent-manager, pi-context-prune, and pi-background-monitor) alongside @earendil-works/pi-tui and @earendil-works/pi-coding-agent (v1.5.2) reveals a recurring architectural tax: every extension that outgrows two boolean toggles ends up hand-rolling its own overlay shell, route stack, height-budget allocator, settings schema validator, atomic file writer, and non-TUI fallback.

Core thesis: pi-extension-settings-dialog should sit directly above @earendil-works/pi-tui as a zero-runtime-dependency TypeScript/ESM library split into three independently usable layers: (1) a declarative schema & hardened layered JSON store, (2) a single-overlay TUI dialog engine with built-in mouse hit-testing, and (3) automatic RPC/non-TUI degradation.

Crucially, the library should not try to absorb domain-specific pickers (such as LLM model registries, MCP server provenance discovery, or YAML agent editors). Instead, it should provide a clean custom field/sub-route escape hatch plus reusable primitives (SearchableList, MultiSelectTree, ConfirmRoute) so extensions keep domain logic lean while sharing 100% of the settings plumbing.

Best Ideas from pi-subagent-manager

  • Override-only layered JSON: Global and Project files store only deltas from the lower layer, so changing a global default automatically propagates to projects that didn't override it.
  • Provenance dots (●): A fixed 3-cell middle column makes Global vs Project inheritance scannable at a glance.
  • Optimistic concurrency (expectedLayers): Refuses to overwrite if another Pi session modified settings on disk while the dialog was open.
  • DialogSession: Lets imperative await dialogMenu(...) flows run inside one stable overlay without flicker.

Best Ideas from pi-context-decisions

  • Pure-data settings-model.ts: Zero pi-tui imports in field metadata and layout math — 100% unit-testable without a terminal.
  • Singleton manager + AbortSignal: Re-invoking the command focuses and navigates the existing overlay; shutdown aborts async loaders cleanly.
  • Hardened persistence: 64 KiB read/write cap, recursive secret-key rejection, terminal control-sequence sanitization on pasted input.
  • Full RPC fallback: Non-TUI clients get a working ctx.ui.select / ctx.ui.input settings menu from the same field metadata.
03 / Platform Internals

What @earendil-works/pi-tui v1.5.2 Gives Us — and Its Gotchas

Auditing the compiled @earendil-works/pi-tui and @earendil-works/pi-coding-agent packages reveals several subtle runtime behaviors that a shared library can hide behind safe defaults.

1. Never call tui.hideOverlay() directly

TuiBase.hideOverlay() unconditionally pops overlayStack[length - 1], regardless of which overlay called it or visual focus order. Always close via the done() callback from ctx.ui.custom(), which invokes overlayHandle.hide() and splices the exact overlay entry safely.

2. Use the injected keybindings argument

ctx.ui.custom((tui, theme, keybindings, done) => ...) passes the host's KeybindingsManager. Importing getKeybindings() directly from @earendil-works/pi-tui can bind to a duplicate module instance and miss user keybinding overrides.

3. maxHeight hard-slices overflow

In compositeOverlays, if component.render(width) returns more lines than maxHeight, Pi slices off the bottom lines — clipping your bottom border and footer hints. The dialog must compute its own height budget from tui.terminal?.rows (and re-read it on every render).

4. ctx.mode vs tui.mode

ctx.mode is "tui" | "rpc" | "json" | "print" (use this to decide overlay vs RPC fallback). Inside ctx.ui.custom, tui.mode is "regular" | "fullscreen" — only "fullscreen" (TuiAltScreen) enables SGR mouse tracking and dispatches handleMouse.

Built-in pi-tui primitives we can reuse directly (zero extra dependencies)
  • Input & Editor: Single-line and multiline text editing with CURSOR_MARKER hardware cursor placement and left-click cursor positioning.
  • fuzzyFilter: Built-in fuzzy search utility — eliminates needing fuzzysort as a runtime dependency for searchable pickers.
  • visibleWidth, truncateToWidth, wrapTextWithAnsi, stripTerminalSequences: ANSI-aware layout and sanitization.
  • Theme tokens: Standardized fg (accent, border, muted, dim, warning, success, error, text) and bg (selectedBg) ensure every extension matches the user's active Pi theme (dark or light).
04 / Proposed Architecture

Three Composable Layers

Rather than a monolithic widget, pi-extension-settings-dialog should be structured as three clean layers with explicit boundaries so pure logic stays testable without a TTY and extensions can opt into only what they need.

Layer 3 · Mode Adapter
openSettingsDialog(ctx, ...)
Inspects ctx.mode & ctx.hasUI. In "tui" mode, mounts a singleton ctx.ui.custom overlay with AbortSignal lifecycle. In "rpc" mode, auto-generates a ctx.ui.select/input menu from the exact same schema. In headless mode, returns structured diagnostics.
Layer 2 · TUI Dialog Engine
SettingsDialogComponent
Single-overlay Frame[] route stack (peer tabs at root + pushed editors/pickers/confirmations), priority height-budget allocator, draft + Ctrl+S or immediate save engine, provenance column, and deterministic render-time hit-region table for fullscreen mouse events.
Layer 1 · Schema & Store
defineSettings() · SettingsStore
Zero-TUI-import declarative field definitions, TypeScript type inference, Global + Trusted Project override-only JSON layering, provenance calculation, optimistic concurrency checks, migrations, and symlink/secret/size-hardened atomic I/O.
Host · Pi Platform
@earendil-works/pi-tui & pi-coding-agent
TUI / TuiAltScreen overlay compositing, SGR 1006 mouse dispatch, Input, Editor, KeybindingsManager, Theme, ctx.isProjectTrusted().
05 / Developer Experience

Declarative Schema & Type Inference

Extension authors should declare settings once — getting runtime validation, TypeScript types, TUI editors, help text, provenance tracking, and RPC fallback menus automatically. 

import { defineSettings, field, openSettingsDialog } from "pi-extension-settings-dialog";

export const mySchema = defineSettings({
  id: "my-extension",                 // ~/.pi/agent/my-extension/settings.json
  title: "My Extension",
  scopes: ["global", "project"],      // project auto-gated on ctx.isProjectTrusted()
  saveMode: "draft",                  // "draft" (Ctrl+S) | "immediate"
  tabs: [
    { id: "general", label: "General" },
    { id: "advanced", label: "Advanced" },
  ],
  fields: {
    enabled: field.boolean({
      tab: "general",
      label: "Enable extension",
      default: true,
      description: "Toggle extension behavior without unloading.",
    }),
    mode: field.enum({
      tab: "general",
      label: "Execution mode",
      default: "opportunistic",
      options: [
        { value: "off", label: "Off", description: "Disable hooks and tools." },
        { value: "opportunistic", label: "Opportunistic", description: "Run only on large tasks." },
        { value: "strict", label: "Strict", tone: "warn", description: "Always enforce policy." },
      ],
    }),
    threshold: field.number({
      tab: "advanced",
      label: "Relevance threshold",
      default: 0.375, min: 0, max: 1, integer: false,
      description: "Minimum score [0..1] to include a candidate.",
    }),
    maxConcurrent: field.integer({
      tab: "advanced",
      label: "Max concurrent jobs",
      default: 8, min: 1, max: 64,
    }),
    model: field.custom<string>({
      tab: "advanced",
      label: "Classifier model",
      default: "",
      experimental: true,             // renders [lab] prefix
      validate: (v) => typeof v === "string" && (v === "" || /^[^\s/]+\/[^\s]+$/.test(v)),
      format: (v) => v || "Not selected",
      openSubroute: ({ value, commit, cancel }) => createModelPickerComponent(value, commit, cancel),
    }),
  },
});

// Fully inferred TypeScript type: { enabled: boolean; mode: "off" | "opportunistic" | "strict"; ... }
export type MySettings = typeof mySchema.Type;

// Inside a Pi slash command:
await openSettingsDialog(ctx, {
  schema: mySchema,
  agentDir: getAgentDir(),
  onApply: (next, meta) => runtime.applySettings(next),
});

06 / Persistence & Security

Global vs Project Layering & Hardened JSON I/O

Settings persistence in an agent harness is a security boundary: untrusted repositories can contain malicious .pi/ directories, symlinks pointing outside the project, or accidentally pasted API keys. The store layer should ship hardened by default.

Two-Layer Resolution & Override Diffing

Effective settings resolve as defaults → global → project (with project skipped unless ctx.isProjectTrusted() is true).

  • Saving to Global persists only keys where value !== default.
  • Saving to Project persists only keys where value !== (global ?? default).
  • Each key carries provenance: "default" | "global" | "project" | "both".
  • Built-in Save scope row and Restore defaults action (deletes the target scope's file cleanly with confirmation).

Defense-in-Depth File Safety

  • Symlink refusal: lstat every path segment + target file; open temp files with O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW (0o600) in 0o700 dirs.
  • Atomic replacement: Write to .settings.<uuid>.tmp, rename into place, cleanup in finally.
  • Size & secret caps: 64 KiB max read/write; reject keys matching /api.?key|token|secret|password|authorization|credential/i.
  • Optimistic locking: Snapshot on-disk layers on dialog open; refuse save if files changed externally while editing.
Session-scoped settings escape hatch: Extensions like pi-background-monitor persist ephemeral limits inside session history via pi.appendEntry() instead of JSON files. Exposing a tiny StorageAdapter interface (load(), save(), deleteScope?()) lets those extensions reuse the entire declarative TUI dialog without touching the filesystem.
07 / Full-TUI Interaction

Making Mouse Clicks First-Class in Fullscreen TUI Mode

In Pi v1.5.2, fullscreen mode (TuiAltScreen, detected via tui.mode === "fullscreen") enables SGR 1006 mouse tracking automatically. When the user clicks inside an overlay, TuiBase.dispatchMouseToOverlay() hit-tests overlays top-down and invokes component.handleMouse(event) with 0-based overlay-local x and y.

How Render-Time Hit Regions Work

Because SettingsDialogComponent.render(width) already computes the exact line index and column span of every tab chip, setting row, and footer action pill, it can populate a flat HitRegion[] array during each render pass at virtually zero cost: 

interface HitRegion {
  y: number;           // 0-based row inside the overlay
  x0: number;          // inclusive start column (visibleWidth)
  x1: number;          // exclusive end column
  kind: "tab" | "row" | "action" | "child";
  id: string;
}

handleMouse(event: TuiMouseEvent): TuiMouseEventResult | undefined {
  // 1. Forward to active child (Input, Editor, or custom sub-route) with local coords
  if (frame.child && inBox(event, childBounds)) {
    return frame.child.handleMouse?.({ ...event, x: event.x - childBounds.x, y: event.y - childBounds.y });
  }
  // 2. Wheel scrolls active list or help/status viewport
  if (event.type === "wheel") {
    scrollBy(Math.trunc(event.wheelDelta ?? 0));
    return { handled: true, render: true };
  }
  // 3. Press claims target (suppresses screen text selection & enables click synthesis!)
  const hit = hitTest(regions, event.x, event.y);
  if (!hit) return { handled: true, render: false }; // keep clicks inside dialog from selecting text
  if (event.type === "press" && event.button === "left") {
    if (hit.kind === "row") selectRow(hit.id);
    return { handled: true, focus: true, render: true };
  }
  // 4. Synthesized "click" (same cell release within 500ms) activates tabs, toggles, pills
  if (event.type === "click" && event.button === "left") {
    if (hit.kind === "tab") switchTab(hit.id);
    if (hit.kind === "action") triggerAction(hit.id);       // "save" | "cancel" | "back"
    if (hit.kind === "row" && (isBool(hit.id) || event.clickCount === 2 || wasSelected)) activateRow(hit.id);
    return { handled: true, render: true };
  }
}
Two subtle Pi mouse details to get right: (1) Returning { handled: true } on "press" is mandatory — without it, TuiAltScreen falls through to terminal text-selection and will not synthesize a "click" event on release. (2) Inside tmux / zellij / screen, Pi intentionally omits \x1b[?1003h (all-motion tracking), so hover "move" events will not fire there; hover highlights must always be progressive enhancement, never required for discoverability.

09 / Scope, Tradeoffs & Rollout

Packaging Strategy & Recommended Rollout

Package Shape

  • Name: pi-extension-settings-dialog (pure ESM, Node ≥ 22, TypeScript sources + declarations).
  • Dependencies: Zero runtime dependencies. Peer deps: @earendil-works/pi-coding-agent >= 1.5.0 and @earendil-works/pi-tui *.
  • Subpath exports: /schema (pure data + validation, zero Pi imports), /store (Node fs layered JSON persistence), /dialog (TUI overlay + mouse), . (all-in-one openSettingsDialog).

Explicit Non-Goals

  • No domain pickers: Model registries, auth credential checks, and MCP server discovery stay in host extensions via field.custom.
  • No secret storage: Credentials belong in Pi's auth store / env vars; the store actively rejects secret-like keys.
  • No layout framework: Don't try to replace pi-tui's general-purpose VStack/HStack — focus strictly on settings dialogs.

Recommended Migration Order (Dogfooding Across the 4 Extensions)

  1. Phase 1 — Build & test on pi-context-prune: Smallest schema, biggest immediate win (gains atomic hardened writes, validation, project scope, ctx.mode RPC fallback, and mouse support while deleting ~180 LOC of SettingsOverlay glue).
  2. Phase 2 — Validate layered provenance & Ctrl+S on pi-subagent-manager: Exercises 2-layer override diffing, provenance dots, optimistic concurrency, Restore Defaults, and field.custom sub-routes for HousekeepingModelPicker and SubagentExtensions.
  3. Phase 3 — Validate tabs, immediate-save & RPC parity on pi-context-decisions: Exercises peer tabs, saveMode: "immediate", singleton focus/navigate, legacy schema migration hooks, and ctx.ui.select/input RPC parity.
  4. Phase 4 — Validate pluggable StorageAdapter on pi-background-monitor: Exercises session-entry persistence (pi.appendEntry) inside the same declarative dialog API.
