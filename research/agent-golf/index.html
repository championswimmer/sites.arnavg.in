01 / THE RECOMMENDATION

Reuse a trajectory format.
Build a small scoring layer.

There is no single verified, drop-in evaluator covering all five agents and all four requested metrics. Use Harbor’s ATIF for interchange, native adapters for collection, and a deterministic Agent Golf reducer for the scoring rules.

ATIF represents user and agent steps, tools, observations, usage and subagents. Harbor documents automatic trajectory generation for Codex and Claude Code. It provides a useful foundation, but does not establish universal export support across these five products. Harbor ATIF documentation.

Trusted mode — implement

Trust the participant’s harness to record the full attempt and report numbers truthfully. Accept native traces, normalized events and supplemental metric reports. Validate formatting and accounting; compute a reproducible score.

Zero-trust mode — defer

Assume a participant can fabricate traces and totals. This document lists abuse scenarios only. Authentication of execution, anti-cheating architecture and prevention mechanisms are future work.

Scope: a submission-and-evaluation backend, collector/adapters, a versioned metric specification and leaderboards. This is a build plan; the backend and collectors have not been implemented or tested against live sessions.

OTel is a collection and transport standard. GitHub documents model/tool traces and input/output usage, with content capture optional. It does not define an Agent Golf competition. GitHub monitoring overview.

Design choice: keep raw evidence and a fine-grained Agent Golf event ledger; export that ledger to a pinned ATIF version. Put golf-specific annotations in extra.agent_golf where supported. 04 / METRIC SPECIFICATION v1

Define the counters before writing parsers.

Attempt: all work from the declared start on the starter repository through the declared final artifact. Include continuations, forks, retries, compaction, subagents and auxiliary inference used to solve the task. Include abandoned work inside that attempt. The participant truthfully declares the boundary in trusted mode.

MetricNormative rule proposed for v1
tool_calls_requestedCount each distinct model/harness-issued tool invocation once, including failed, denied and cancelled requests. Results and stream updates are not new calls. Expose executed, succeeded, failed, denied and cancelled breakdowns separately.
human_prompt_countCount each submitted human instruction or steering message once, including a repeated identical prompt. Exclude tool results, generated summaries, system instructions and subagent delegation messages. Track permission-only clicks separately. Built-in navigation commands are not prompts; commands that instruct model work are.
human_prompt_charsSum Unicode code points of submitted human text, after CRLF/CR → LF. Preserve spaces and trailing newlines; no trimming or Unicode normalization. Python len(text) after newline normalization; JavaScript [...text].length. Count typed template invocation text; record expanded content separately.
model_requestsCount actual dispatched inference requests, including paid failures, retries, compaction and nested model work. UI assistant messages, reasoning chunks and ATIF steps are not equivalent to requests. Unknown if only aggregate usage exists.
agent_cyclesOptional harness-specific human-prompt-to-yield cycles. Display descriptively; never compare unnormalized vendor “turns.” Use model_requests for the Model-call Golf board.
total_tokensSum input and output with cache counted exactly once and reasoning counted according to its inclusion relationship. Include every request in the attempt. See the accounting contract below.

Three parallel tool invocations count as three. One shell invocation containing ten commands counts as one tool call. A delegation invocation plus five child tool invocations counts as six. This is an interface metric, not a measure of computational work; compare tools primarily within a fixed harness/configuration.

Prompt length versus supplied context

Record task_prompt_chars, participant_context_chars, attachment bytes and expanded-template characters separately. Keep organizer-supplied task text separate from human instructions. Rules files, skills, pasted files and image attachments can add large context without increasing typed prompt length. Their model input tokens still count. Start Prompt Golf with text-only inputs and a fixed, declared rules/skills configuration; use a separate open-context division if students may customize it.

“Code generated” needs three named measurements

MeasurementHow to calculateWhat it does not mean
emitted_code_lines
Optional		Lines in explicitly identifiable code payloads emitted by the model: write content, added patch lines and tagged code blocks. Exclude patch context/headers. Count repetitions if the model generates the same code twice; deduplicate streaming copies.Not universally measurable. Code embedded in shell strings and ambiguous prose may be unclassifiable. Report partial coverage rather than pretending code-fence counting is complete.
gross_added_source_lines
Recommended activity metric		Sum added source lines across successful file mutations observed by the harness, using before/after snapshots or complete mutation reports. Rewrites count again; removals are a separate total. Include eligible new files.A write-activity proxy, not proof of model authorship. Code generators and shell writes must be covered or flagged. A final diff cannot reconstruct this.
final_added_source_lines
Recommended result metric		Added lines in a reproducible starter-to-final diff, over a pinned file manifest. Report removed lines and final source LOC separately. Use snapshots, not only tracked-file status.Not gross generation: 100 lines written, deleted and replaced with 20 can yield only 20 final added lines.

Line policy: v1 counts physical nonblank lines in allowlisted source paths, including comments; normalize newlines, count an unterminated final line, and pin the diff algorithm and rename policy. Exclude binaries, vendored dependencies, lockfiles and build output using the task’s manifest. This is intentionally a defined source-line measure, not a language-independent statement count. Track tests and configuration separately. Concurrent edits need serialized mutation records or batch attribution; if only periodic snapshots exist, flag gross LOC as partial.

Keep LOC as a descriptive metric in v1, not a ranking objective. Otherwise minification, code formatting, generated files and code reuse can dominate the competition for reasons unrelated to agent efficiency.
05 / TOKEN ACCOUNTING

Cache is a category, not always an extra.

Normalize to disjoint input buckets and one inclusive output bucket. Preserve raw provider fields and their inclusion semantics alongside the normalized value. Anthropic separates ordinary input, cache creation and cache reads in usage. Codex’s JSON interface reports input, cached input and output. Anthropic cache accounting; Codex events.

T = U + R + W + O

U = uncached input excluding cache creation · R = cache-read input · W = cache-write input · O = all output, including reasoning when reported.

Source contractNormalization
Input already includes cache reads/writesU = input − R − W; total is input + O. Unknown cache split does not invalidate a known inclusive input total.
Input excludes separately reported cache reads/writesU = input; total is input + R + W + O.
Reasoning is a subset of outputKeep it as an informational subfield. Do not add it again.
Reasoning is explicitly excluded from outputAdd it once to construct O. If the relationship is undocumented, report the complete total as unknown until the harness supplies the contract.
Cache duration sub-bucketsA 1-hour creation field may be a subset of total cache writes. Store the breakdown; do not blindly add every field.

Try the accounting

Illustrative numbers, not a provider benchmark. Change the input convention to see why identical field names can produce different totals.

Reducer rules that avoid accidental overcounting

  1. Choose one authoritative source per coverage scope. Prefer complete per-request usage; otherwise use a declared turn/session aggregate or harness report. Never add aggregate totals to the requests they already contain.
  2. Use finalized request records. Streaming chunks may repeat cumulative usage. Join by session, agent and request identity; sum finalized records once. Retries are distinct requests, even with the same prompt.
  3. Delta cumulative counters only within a documented epoch. Record process restarts, reset points and start baselines. A decreasing counter needs an explicit reset, not silent clamping. Histogram sample counts are not token totals.
  4. Include child and auxiliary work once. A parent may already include child usage. Require a scope declaration and request references when available. A nesting relationship alone does not tell you what a total includes.
  5. Never retokenize visible chat as actual usage. It misses hidden context, repeated input, tools, reasoning and compaction. Optional estimates belong in separate fields and do not qualify for Token Golf.
  6. Unknown is null. Publish coverage for total usage and each breakdown independently. A known total with an unknown cache split can rank; an unknown total cannot. Zero means measured zero.

For example, two requests with 10,000 input tokens each count 20,000 input tokens, even if they reuse the same context. Cached tokens still count in Token Golf. A separate cost view may discount cache hits using a versioned price table, but subscription fees and Copilot billing multipliers are not token counts.

06 / THE COMPETITION

Correctness first. Then choose the objective.

Every ranked submission must pass the task’s required correctness checks. In trusted mode, accept the harness’s report of running the pinned verifier against the final artifact. Store the verifier version, result and artifact digest. Server-side execution is optional future functionality, not a prerequisite for trusting the student’s run.

BoardAscending sort keyRequired complete fields
Agent Golf / default(total_tokens, human_prompt_count, human_prompt_chars)All three; correctness passed.
Prompt Golf(human_prompt_chars, human_prompt_count)Both; fixed context rules.
Model-call Golfmodel_requestsRequest count.
Tool Golftool_calls_requestedRequested-call coverage, including failures/denials.

Lexicographic ordering gives a clear default: save tokens first, use fewer human interventions to break ties, then use less human text. Exact ties share a rank. Also show all metrics side by side and optionally a Pareto view. Do not add raw tokens, characters and calls into an unexplained weighted sum.

Comparable divisions

  • Controlled: same task version, starter, model snapshot/provider, reasoning settings, harness/version, tools, context policy and cache policy. Best for comparing student prompting strategies.
  • Open harness: approved models and harnesses, fully declared configuration. Useful for end-to-end system efficiency; different tokenizers and system prompts mean it is not a clean measure of prompt quality alone.
  • Fixed attempt policy: v1 ranks the best eligible submitted attempt; all work inside each attempt counts. Unlimited practice is permitted and this is disclosed. A future limited-attempt contest needs a separate policy.

Publish the rules before the competition. A cache-inclusive token objective avoids a direct scoring discount for a warmed cache, but provider nondeterminism remains. Optional repeated-run evaluation should be a separate competition format, with its own aggregation and failure policy.

07 / TRUSTED MODE — BUILD THIS

The student owns the harness.
The backend owns the definitions.

Trust both trace authenticity and truthfully reported missing measurements. Do not require managed execution, remote attestation, API interception or proof that a trace could not have been edited. The implementation checks data quality and mathematical consistency, not honesty.

Participant workflow

  1. Choose a task and division. Download the task specification, starter reference, verifier and metric policy.
  2. Use the proposed collector to start an attempt, or integrate the report schema into an existing harness. Record harness/model versions and begin/end boundaries.
  3. Work normally. Capture prompts and native events. Attach fork/child sessions and any harness-measured counters unavailable in the export.
  4. Run the specified verifier locally. Capture final files/diff and the verifier report.
  5. Preview the bundle: metrics, unknown fields, excluded files and content to be uploaded. Redact secrets before upload; calculate lengths before redaction.
  6. Submit. The backend returns a metric report and board eligibility, or precise accounting errors to fix.
# Proposed Agent Golf commands — to be implemented, not existing tools.
agent-golf init --task url-shortener-v1 --agent pi
agent-golf capture -- pi
agent-golf finish --verifier task/verifier.json
agent-golf inspect submission.agolf.zip
agent-golf submit submission.agolf.zip

# Existing sessions can be imported without rerunning the agent.
agent-golf import --agent claude-code --trace session.jsonl
# Missing measurements may be supplied as truthful harness reports.

Evidence modes inside trusted mode

Submission formWhat the backend does
Native trace + manifestDetect adapter/version, derive the available metrics, request a report for missing fields.
Normalized ledger / ATIF + extrasValidate the schema, normalize usage and reduce without needing a native parser.
Trace + supplemental harness reportAccept reported measurements for explicitly uncovered scopes. Display provenance; do not double count.
Summary report with attached trace referenceAccept complete, well-defined reported values even if the parser cannot derive them. Mark harness_reported, not independently verified.

All four are trusted submissions. Source labels are explanatory, not anti-cheating tiers. For a disagreement between overlapping reported and derived totals, return accounting_conflict with both values and scopes; do not silently choose the smaller number. The participant can correct the scope or adapter mapping.

Privacy: raw traces stay private by default. Publish only chosen display names, scores and non-sensitive configuration. Store redacted text plus trusted original character counts when necessary. Missing or redacted content need not block scoring when the harness truthfully supplies the required measurements.

A small bundle with explicit provenance.

Illustrative placeholders. The schema must additionally allow configuration digests, provider/account mode, collector and adapter versions, file manifests, redaction declarations, parent sessions and usage epochs. Digests provide reproducible identity in trusted mode; they do not prove honesty.

Enums: source = trace_derived | harness_reported | artifact_derived | estimated | unavailable; coverage = complete | partial | unknown. Complete means complete under the declared contract, not authenticated. Keep a known partial subtotal as observed_value while the complete value is null. A reported total may be complete while its breakdown is unknown.

Normalized ledger

Every event has event_id, attempt_id, session_id, agent_id, parent_event_id, timestamp, type and source reference. References identify the raw file digest and record index. Use stable original IDs when available; a fallback identity must include record position and lifecycle, not just message content.

tool_invocationCall ID, tool name, actor, lifecycle/status, parent request; optional mutation references.

ATIF mapping

Map human instructions to user steps, model activity to agent steps, tool invocations/results to calls/observations and normalized usage to the compatible metric fields. Preserve request IDs, bucket inclusion semantics, prompt origins, scope and LOC in extra.agent_golf or the sidecar. Pin ATIF and adapter versions; validate round trips on the subset of fields the chosen ATIF version represents. Never derive model request counts from the number of ATIF steps.

09 / BACKEND ARCHITECTURE

Batch uploads first. Deterministic reduction.

1 · Upload APIAccept manifest and bundle; store immutable original bytes.
2 · Parse workerValidate packaging; select native adapter or generic report importer.
3 · Metric reducerNormalize scopes and usage; compute counts; reconcile reports.
4 · Results APISave versioned evaluation, eligibility and leaderboard entries.

The upload creates a queued job. The worker reads object storage, writes a normalized ledger, then runs a pure reducer. PostgreSQL stores submission metadata and summaries; large raw/event files remain in object storage. Results and leaderboard queries read persisted evaluation rows. A normalizer bug can be fixed by reprocessing the original bundle into a new evaluation version.

Suggested MVP stack

  • Python API + worker: FastAPI/Pydantic for typed contracts and validation; pure Python reducers and adapters. Reuse Harbor’s trajectory models where useful.
  • PostgreSQL: tasks, submissions, evaluations and a leased jobs table. Start with a database-backed queue; no separate messaging system required.
  • S3-compatible object storage: bundles, traces, normalized JSONL, reports and final artifacts.
  • Simple web UI: upload, inspect a submission, compare metrics and filter leaderboards. Streaming OTel ingestion and external observability dashboards are optional later.
  • Deployment: API container, worker container, Postgres and bucket. Scale workers with queue depth. Set maximum upload size, event count and parsing time as configurable limits.

Endpoints

Database model

tasks and divisions hold versioned rules. submissions records owner, attempt, object key, digest and state. evaluations stores immutable metrics JSON, provenance, eligibility, reducer/adapter versions and verifier status. jobs stores lease, retries and last error. Index task/division/policy and selected numeric score columns. Enforce uniqueness on submission plus evaluation-version tuple; use transaction boundaries for publishing a completed evaluation.

Operational details

Use bounded retries for transient storage/database failures; deterministic parse errors become needs_correction. Never run uploaded scripts to parse a trace. Handle archives with path, size and decompression limits; escape trace text in the UI. These are ordinary service hygiene, not a zero-trust anti-cheating system. A local verifier report is data: the backend does not need to execute the student’s program in v1.

Proposed retention: private raw bundles for the course term plus 30 days, then delete by policy; keep aggregate scores only with participant consent. Make this configurable. For a planning example, 100 students × 10 attempts × 20 MB ≈ 20 GB of raw storage before replication and derived files. Measure actual bundle sizes before choosing quotas or estimating costs.

Fixtures that matter

  • Unicode prompts, multiline input and repeated identical human messages; control clicks versus instructions.
  • One response split into streamed chunks and multiple content blocks; repeated usage updates; resumed counter epochs.
  • Parallel calls, failed/denied calls, nested agent usage and aggregate/child overlap.
  • Inclusive versus exclusive cache inputs, cache-write sub-buckets, reasoning inclusion and missing totals.
  • Branch/fork attempts, compaction costs and partial capture with a truthful supplemental report.
  • A new untracked source file, a rewrite then deletion, a shell-generated file, binaries and excluded lockfiles.
  • Correctness failure despite a low token score; equal scores; incomplete-field board eligibility.

Example pilot task

Use a small URL-shortener repository with fixed dependencies. Require create-short-link, redirect and invalid-input behavior, plus deterministic persistence checks. Ship a verifier manifest and tests; trusted participants report the result against their final artifact. Keep external network services unnecessary. The local test approach can follow Harbor’s task/verifier conventions without making Harbor the upload backend.

MVP exit: an honest participant can submit a session, understand exactly how each metric was counted, fill genuine export gaps, pass the correctness gate and appear on the appropriate board. Adding an agent should require a new adapter or report exporter, not a new scoring engine.

11 / ZERO-TRUST MODE — DEFERRED

Abuse scenarios to revisit.
No prevention design yet.

Per scope: zero-trust implementation is not required now. Do not add managed runners, cryptographic attestation, provider-side reconciliation or anti-cheating infrastructure to the trusted-mode milestones. The list below is a future threat-model backlog.
Possible abuseWhat becomes falseQuestion for later
Fabricated JSONL or edited metric reportPrompts, calls or token counts never occurred as reported.What would establish authentic execution?
Deleted expensive requests, failed turns or branchesA locally plausible trace understates the attempt.How could completeness be established?
Omitted subagents, compaction or off-session model callsWork is outsourced beyond the declared boundary.Which external work should count, and how could it be observed?
Code or solution prepared before captureThe trace records only the final cheap step.What constitutes the real start of an attempt?
Different final artifact from the one in the traceReported code and submitted solution do not match.How could artifact provenance be established?
Forged verifier results or modified testsA failing solution qualifies as correct.Who must execute and control verification?
Hidden rules, skills, attachments or external human helpA tiny visible prompt conceals the actual instructions.What assistance is allowed and measurable?

Trusted mode deliberately accepts the honesty assumption behind these scenarios. Structural checks can catch mistakes, but a valid schema, matching checksum or internally consistent trace is not evidence against deliberate fabrication.
