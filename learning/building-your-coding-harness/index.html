This is the core of every coding agent. The task: "fix the failing login test". The file names, test output and the fix itself are illustrative, and the size bar has no real numbers. The loop structure is pi's real code path. Step 1 (Input): you type one line. pi first checks for built-in and extension slash commands, expands skills and prompt templates, then builds the user message. Step 2 (Context): the harness assembles what the model sees. The system prompt comes from buildSystemPrompt: tool snippets, guidelines, AGENTS.md context files, skills, the cwd. Then the tool definitions and the message history. The model knows only what is in this stack. Step 3 (Provider): pi-ai turns that provider-neutral context into an HTTP request for Anthropic, OpenAI, Google, Bedrock or others. Note the label on the right: the whole stack is sent on every call, not just the new message. Step 4 (Stream): the answer streams back as normalised events: text deltas, thinking deltas, tool-call deltas. Here it says it will run the tests and emits a tool call for bash. Step 5 (Tool calls): the harness looks up the tool, validates the arguments against its schema, and runs it. pi runs multiple tool calls in parallel by default. Step 6 (Tool results): the output is wrapped as a toolResult message and appended. Because there were tool calls, the loop goes back to Context and calls the model again. Steps 7–8: two more laps: read the file, then edit it. Watch the context stack: the test log and the whole file are still in there, and they are re-sent on every later call. Hold that thought; the context-prune extension later in the talk deals with exactly this. Step 9–10: the model replies with plain text and no tool calls, so the inner loop exits and the run is done. Between laps pi can also auto-compact if the context gets too big, and after the run it may retry an error. One prompt from you, four model calls, three tool runs, all driven by the harness. The model

the only part you don't build

pi is split into npm packages, and each one is a layer of the harness. We'll light them from the bottom up. Step 1, pi-ai: the provider abstraction. It takes a provider-neutral context (system prompt, messages, tools), builds the Anthropic, OpenAI, Google or Bedrock request, and streams back one normalised event shape: text, thinking and tool-call deltas, then done or error. Nothing above this layer sees provider wire formats. Step 2, pi-agent-core: the generic agent loop from the previous slide. Stream the assistant message, run the tool calls, append the results, repeat. It has no UI and knows nothing about coding. Step 3, pi-coding-agent's AgentSession: this turns the generic loop into a coding agent. It adds the coding tools, JSONL session files that store a branching tree, compaction, retries, the system prompt, and the extension runner. By default the model gets four tools: read, bash, edit and write. grep, find and ls exist but are off by default. Step 4, the terminal UI: renders the transcript, the editor, the footer and widgets, and handles built-in slash commands. The same AgentSession also runs without the TUI in print mode, RPC mode, or embedded through the SDK. Step 5: all four layers are the harness. The model sits outside, at the end of an HTTP call. It is the one piece you rent rather than build.

How does dispatch actually work? Every handler for an event runs one after another, in extension load order, and each one is awaited. Step 1: ext A just observes. It reads the event and returns undefined, so nothing changes. Most events, like message_update, turn_end and agent_end, are observe-only. Step 2: ext B intervenes. For context it returns an object with messages, and pi swaps that in. Here 12 messages become 7. The numbers are illustrative; this is what pi-context-prune does for real. Step 3: the result is chained. ext C receives B's version, not the original. context, tool_result and before_agent_start's systemPrompt all chain like this. tool_call is different: the first handler that returns block wins, and pi stops asking the rest. Step 4: pi uses the final value. For context it's a deep copy, so the session file on disk never changes. Step 5: gotcha. Handlers are awaited, so an expensive handler slows the whole loop. That includes message_update, which fires on every streamed delta. That's why speedometer throttles its footer updates. Step 6: failures are safe. A handler that throws is caught, reported, and the agent carries on. The one exception is tool_call, which has no try/catch in the runner: if your tool_call handler throws, that tool call becomes an error result. It fails closed, which is what you want from a guard.

This is the slide that explains why the default mode batches instead of pruning eagerly. Token numbers are illustrative; the rewrite counts follow straight from the mode definitions. [0] The rule providers give us: a cache hit needs the earlier prompt prefix to be byte-identical. Append to the end and you keep the hit. Change something earlier and the provider recomputes from the point of the change onward, and pays to write that new prefix into the cache. That is exactly what pruning does: it edits earlier messages. The extension's README says it plainly: pruning too often saves in-context tokens while still hurting latency and cost. [1] every-turn flushes inside turn_end, after every tool-using turn. Four tasks of three tool turns means twelve rewrites and twelve summarizer calls, and pi awaits each one, so it sits in the critical path of the turn. Look at the pattern: the prefix is never left alone for more than one request, so the cache never earns anything back. The mode guidance in the code says exactly this: "Debugging only. Prunes after every tool turn, which is easiest to inspect but churns provider prompt caches the most." [2] agent-message, the default: flush once, on the first assistant message with no tool calls. One rewrite per task instead of one per turn. The request right after the flush is the one that pays, and it is the cheapest one to pay for, because it is the small pruned request: about 3,000 tokens instead of 14,000. Then the rest of that task appends on top of it and hits the cache every time. [3] Here is the part people miss. The summaries are not outside the cache. After the flush, the new, shorter prefix, summaries included, is what gets written to the cache, and those green blocks are then read from cache for the whole rest of the batch. [4] And it compounds. Each batch's floor sits higher than the last, because the summaries from earlier batches are already cached and never change again. So over a long horizon you are not fighting the cache, you are climbing a staircase: rewrite once, re-cache small, reuse for a whole batch, repeat. The cache builds up fine. That is the opposite of every-turn, which resets before the cache is worth anything. [5] So the guidance is: batch the prune. agent-message batches per task, on-context-tag per milestone, agentic-auto lets the model pick the boundary, and its system prompt says to aim at 8 to 12 related tool calls and warns that calling context_prune after every 2 or 3 hurts prompt-cache efficiency. Worth saying out loud: no pruning at all is perfectly cache-friendly, because it only ever appends. The reason we prune anyway is the other three costs from the problem slide: attention, the window, and re-reading a 30,000-token prefix on every single request.
