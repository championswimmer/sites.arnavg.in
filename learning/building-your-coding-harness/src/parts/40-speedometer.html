Third and final extension, and the lightest one. After context-prune, which changes what the model sees, this one changes nothing at all. It answers a question everyone has asked: how fast is my model, really, on my own workload inside my own harness, rather than on a benchmark page? The pill shows the exact string the extension writes into pi's status bar: tokens per second and time to first token. Install line if anyone asks: pi install npm:@championswimmer/pi-speedometer.

Step 0: Hook question. Your agent feels slow. Is it slow before the first token arrives, or while tokens are arriving? Those are two different problems with two different fixes. Step 1: TTFT, time to first token. The clock starts when pi sends the request and stops when the first piece of the answer shows up. It covers the network, queueing at the provider, and the model reading your whole prompt, which is prefill. A big context means a big TTFT. Step 2: TPS, tokens per second: output tokens divided by the seconds since the first token. That's decode speed: how fast the model types once it has started. Step 3: The diagnosis. High TTFT points to a huge context, a cold cache, a busy provider or a slow network. Low TPS points to a big or slow model, heavy thinking, or an overloaded endpoint. Two numbers, and you know which knob to turn. The bar proportions match the walkthrough on the next slide: 840ms of waiting, then 3.36 seconds of streaming. Those numbers are illustrative.

All numbers are illustrative but internally consistent, from the research walkthrough: first delta at 840ms, a delta every 20ms, 168 deltas, message_end at 4.2 seconds with 310 output tokens. Step 1, t = 0: pi fires before_provider_request right before the HTTP call. That hook is meant for inspecting or rewriting the payload; we just use it as a starting gun. performance.now(), reset a few variables, return nothing. Step 2, the wait: message_update events of type start and text_start can arrive, but they carry no content, so the handler ignores them. This dead air is network, queueing and prefill of your whole context. Step 3, 840ms: first text_delta. Freeze TTFT at 840ms. There's no TPS yet because zero seconds have passed since the first token, and the code guards against divide-by-zero, so for one frame the footer shows only the stopwatch. Step 4, 2.14s: deltas arrive about 50 times a second. Repainting the footer that often is waste, so it throttles to 250ms; with deltas on a 20ms grid that is a render every 260ms. Point at the maths: 122 tokens divided by 1.30 seconds since the first token is 93.8. 168 deltas produce only 13 status writes. Step 5, 4.2s: message_end carries the real usage: 310 tokens over 3.36 seconds is 92.3 tokens per second. That final value stays in the status bar after the turn. In an agent loop, the next LLM call fires before_provider_request again and re-anchors the clock. Demo: click "replay in real time" to run the full 4.2 seconds at real speed; 0.25× slows it down so people can watch the footer tick. Caveat, say this only if asked: live TPS depends on the provider reporting partial usage. Google sends usage on every chunk; OpenAI chat completions only in the final chunk, so the extension estimates chars ÷ 4 until message_end snaps to exact. The README says Anthropic streams cumulative output counts, but pi's Anthropic adapter appears to set usage.output only at message_start (usually 1) and at the final message_delta, so the mid-stream number could read very low, like 3.8 t/s, until message_end fixes it. Test with a live Claude run before claiming exact live TPS on Anthropic. The final number is correct either way.

This is every hook the extension registers. Bodies are elided; the skeleton is lines 116 to 194 of the single source file. Step 1: before_provider_request starts the clock. requestStart = performance.now(), and it resets firstDeltaTime, the throttle timestamp, the token count and TTFT. It ignores the payload and returns undefined, so the request goes out unchanged. Step 2: message_update. It returns early unless the stream event is a text, thinking or tool-call delta. On the first one it records firstDeltaTime and computes TTFT. On every one it updates the token count, and only if 250ms have passed does it call renderStatus, which does tokens divided by seconds since the first delta and calls ctx.ui.setStatus with the key "speedometer". Step 3: message_end. It fires for user and tool-result messages too, so it checks role is assistant. It snaps the token count to message.usage.output, which is the exact number, and does one final unthrottled render. Step 4: agent_end and session_shutdown just set streaming to false and leave the final numbers in the footer. /speed toggles each metric on or off and switches icon or text labels, saved to ~/.pi/agent/pi-speedometer.json. Stats: 233 lines total, one file, no runtime dependencies and no build step, because pi loads the .ts directly. Of that, settings load/save is about 45 lines and /speed about 40; the actual measurement logic is about 55. Optional aside, "even tiny extensions have edge cases": after /speed toggles, the re-render passes performance.now() as the end time rather than when the stream ended. So toggling a label 60 seconds after a response recomputes TPS over 63 seconds and shows something like 4.9 t/s. The fix is storing the end time at message_end: a one-line PR.

no live usage? estimate, then snap to exact at message_end

Step 0: What does the extension actually read? Every chunk of the stream reaches extensions as a message_update event, and inside it is an assistantMessageEvent with a type. There are about a dozen types: start, text_start, text_delta, text_end, the same trio for thinking and for tool calls, then done or error. Step 1: The filter. Only three types carry new content: text_delta, thinking_delta and toolcall_delta. That set is literally called CONTENT_DELTAS in the code. Everything else is dropped. Two consequences worth saying out loud: a thinking token counts as the first token, so TTFT here means "first sign of life", not "first visible answer text"; and tool-call arguments streaming in count toward TPS too. Step 2: The shape. Each delta event carries the delta string and partial, which is the whole assistant message so far, including its usage block. Step 3: Counting. If the provider reports a running output-token count, use it: exact. Google, for example, sends usage metadata on every chunk. OpenAI chat completions sends usage only in the final chunk, so until then the extension estimates characters divided by four, and message_end snaps it to the exact count. Caveat for the speaker, not the slide: the README says Anthropic streams cumulative counts, but in pi's Anthropic adapter usage.output looks like it's only set at message_start (usually 1) and at the final message_delta. If so, the live number reads very low mid-stream and only becomes correct at message_end. Verify with a live Claude run before promising exact live TPS on Anthropic. The code shown is lightly trimmed: the original also checks that message.usage exists.
