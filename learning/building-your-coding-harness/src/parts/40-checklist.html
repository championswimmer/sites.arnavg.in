Long tasks drift. Plans don't.

Without a plan, compaction and long tool chains blur the goal

With a checklist, the plan is data the agent keeps re-reading

Plan, stay on track, and let the harness enforce order

Step 0: Set the scene. Give an agent something like "add rate limiting to the API". That's several steps: pick a strategy, write middleware, wire it in, test it. Step 1: Without a plan, the goal only lives in the transcript. Forty tool calls deep, or after compaction has summarised the early turns, the agent can lose the thread. The path drawn here is illustrative, not measured. Step 2: With pi-checklist, the model writes the plan down as tasks with 3-char ids: stg, mid, wir, tst. That's the scenario we'll walk through. Step 3: Three reasons it helps. First, checklist_create makes the model break the work down before touching code; the tool guideline says to use it "at the start of multi-step work". Second, before_agent_start re-injects the open tasks into the system prompt on every user prompt, so after compaction the model still sees "stg ongoing; mid blocked ← stg". Third, dependencies are enforced: the model can't start or finish a task whose prerequisites aren't done. It gets an error it can read and fix. Also worth saying: the human gets a live view of progress without scrolling the transcript. It's a small working list, not a project-management app.

Step 0: Before any code, here's where this extension plugs in. The model on the left, pi in the middle with the extension inside it, your terminal on the right, and the session file underneath. Step 1, tools: pi.registerTool three times: checklist_create, checklist_read, checklist_update. Each has a description, a one-line promptSnippet for the "Available tools" list, promptGuidelines bullets appended to the system prompt's Guidelines, and a TypeBox parameter schema. The model now has abilities it didn't have before. Step 2, prompt: a before_agent_start handler fires once per user prompt, before the agent loop, and returns a new systemPrompt. It appends a one-line usage hint and, if any task is still planned or ongoing, a live snapshot of the open tasks, capped at 8. Step 3, UI: the human side. renderCall and renderResult replace the default tool-call rendering with a compact "checklist stg" line and a "0/4 done, 1 ongoing" summary. ctx.ui.setWidget draws the list below the editor, ctx.ui.setStatus puts "☑ 0/4" in the footer, and registerCommand adds /checklist with show, hide, clear and settings. Step 4, state: every change calls pi.appendEntry("pi-checklist", snapshot). In the JSONL that's a custom entry. Custom entries are never sent to the LLM. The snapshot also goes into the tool result's details. Remember this one; it's why the list survives branching. Contrast so far: speedometer only observes; checklist adds abilities, UI and state. This is the whole extension in one scenario. Every tool text and error string on this slide is real output from running the extension's store and tool code. Step 0: The user types "add rate limiting to the API" and presses Enter. No checklist exists yet. Step 1: before_agent_start fires once per user prompt, before the agent loop. There's no list, so it only appends the moderate usage hint. The promptGuidelines bullets from the three tools are already in the Guidelines section. It's plain text and costs very little. Step 2: The model calls checklist_create. It passes explicit 3-char ids because the dependencies point at tasks created in the same call, which is exactly what the tool guideline recommends. Without explicit ids it would get hashed ids like q6z. The content text goes to the model. The details field holds the full snapshot: it's saved on the tool result and drives the renderer, but it isn't sent to the model. commit() appends a pi-checklist entry, the widget repaints, and the footer shows ☑ 0/4. stg is ready; the rest are blocked. Step 3: The guideline says mark a task ongoing before starting it, so the human always knows what the agent is doing now. The call renders as "checklist stg". On the next user prompt, the injected snippet lists the open tasks, so even after compaction the model still sees the plan. Step 4: Here the model jumps ahead and tries to mark stg done and wir done in one batch. wir depends on mid, and mid isn't done, so the store throws. pi turns the thrown error into isError: true, and the model reads the exact message on screen. Because updates are all-or-nothing, even the valid stg → done is discarded. commit() never runs, so no entry is appended and the widget doesn't change. The extension enforces order; it doesn't just record it. Step 5: The error named the blocker, [mid]. The model finishes stg and starts mid in one call. Order within a batch matters: stg done first, then mid ongoing succeeds. The reverse order would fail. Footer: ☑ 1/4. Step 6: Fast-forward through three more updates to ☑ 4/4. On the next user prompt nothing is planned or ongoing, so before_agent_start appends only the hint and no task snippet. export function loadFromBranch(branch: BranchLike[]) {
  let found = { v: 1, checklist: null };
  for (const entry of branch) {  // root → leaf
    if (entry.type === "custom" &&
        entry.customType === "pi-checklist") {
      found = entry.data;
    } else if (entry.type === "message" &&
        entry.message?.role === "toolResult" &&
        CHECKLIST_TOOLS.has(entry.message.toolName)) {
      found = entry.message.details;
    }
  }
  return found;                  // last snapshot wins
}

This is the part that makes the extension feel native. There's no database and no sidecar file. The session JSONL is the database. Step 0: Each node is an entry in the session file. Teal diamonds are snapshot entries: the pi-checklist custom entry from appendEntry, and the checklist tool result whose details hold the same snapshot. In the real file each mutation writes both; I've drawn one diamond per mutation. The error node from our blocked update has no diamond, because nothing was committed. Sessions in pi are trees: /tree lets you jump back to an earlier message and continue from there, so there are several leaves. Step 1: On session_start (startup, /resume, /new, /fork) and on session_tree, the extension calls reconstruct. That uses ctx.sessionManager.getBranch(), which returns only the entries from the root to the current leaf, walking parentId back from the leaf and reversing. loadFromBranch scans oldest to newest and keeps the last snapshot it sees. On the main branch that's ☑ 4/4. It deliberately avoids getEntries(), which would mix in other branches. Step 2: Say the user thinks a fixed window would have been simpler and uses /tree to go back to just after stg went ongoing. pi moves the leaf; nothing is deleted, and the greyed-out entries are still in the file. session_tree fires, the walk finds the "stg ongoing" snapshot as the last one on this path, the widget repaints to 0/4, and the next before_agent_start injects that older plan. The model on the new branch sees the plan as it was at that point. Step 3: Branch from before checklist_create and there's no snapshot on the path, so the checklist is null and the widget and footer are cleared. Click any node to re-run the walk from there. Compaction only appends a summary entry, so snapshots stay on the path. Live demo option: after the rate-limit demo, open /tree, pick an earlier user message, and watch the widget and footer rewind.

pi.registerTool({
  name: "checklist_create",
  description: "Create or extend the session task checklist (replace by default, or append). …",
  promptSnippet: CREATE_SNIPPET,
  promptGuidelines: CREATE_GUIDELINES,
  parameters: ChecklistCreateParams,
  async execute(_toolCallId, params, _signal, _onUpdate, ctx) {
    const mutation = executeCreate(state.checklist, state.widgetVisible, params, /* prefs */);
    commit(mutation.snapshot, ctx);
    return { content: [{ type: "text", text: mutation.text }], details: mutation.snapshot };
  },
  renderCall: (args, theme) => renderCreateCall(args, theme),
  renderResult: (result, { expanded }, theme) => renderChecklistResult(result, expanded, theme),
});

src/index.ts:307-323 (comments removed, hint strings shortened)


pi.on("before_agent_start", async (event, ctx) => {
  const hint = usageGuidanceAtLoad === "aggressive"
    ? "Checklist expected: use checklist_create/read/update for almost every task…"
    : "Checklist available: … track it with checklist_create/read/update and mark progress…";
  const checklist = state.checklist;
  const open = !!checklist && checklist.tasks.length > 0 &&
    checklist.tasks.some((t) => t.status === "planned" || t.status === "ongoing");
  const extra = open ? ` ${buildInjectSnippet(checklist!)}` : "";
  return { systemPrompt: `${event.systemPrompt}\n\n${hint}${extra}` };
});

function persistSnapshot(snapshot: ChecklistSnapshot): void {
  try {
    pi.appendEntry(CUSTOM_TYPE, snapshot);   // "pi-checklist"
  } catch {
    // Ephemeral/print sessions have no session file — in-memory still works.
  }
}

function commit(snapshot: ChecklistSnapshot, ctx: ExtensionContext): void {
  state = snapshot;
  persistSnapshot(snapshot);
  refreshUi(ctx);
}

Three excerpts, one at a time. The tabs are clickable if you want to jump. Step 0, registerTool: everything the model sees comes from this object. The description, a one-line promptSnippet in the "Available tools" list, promptGuidelines bullets appended to the Guidelines section (pi's docs say each bullet must name the tool, never "this tool"), and a TypeBox schema for the parameters. There are three of these registrations: create, read and update. Step 1, execute: run a pure store function, commit the new snapshot, and return two things. content is the text the LLM reads. details is structured data that isn't sent to the LLM but is saved on the tool-result entry. Validation errors are thrown from the store before commit runs, so pi reports them to the model as isError and nothing is persisted. Step 2, renderers: renderCall and renderResult are the human-facing half of the same registration. Instead of a raw JSON dump you see "checklist create 4 task(s)" and "0/4 done 0 ongoing 1 ready 3 blocked", read from result.details. Step 3, before_agent_start: it fires once per user prompt. It returns a new systemPrompt: the original, plus the hint, plus the open-task snippet if anything is planned or ongoing. System-prompt changes chain across extensions. The usage mode is captured at load, so changing it needs /reload. Step 4, appendEntry: commit does three things: update the in-memory cache, append a "pi-checklist" custom entry, and repaint. The try/catch matters because print or ephemeral sessions have no file. The custom entry covers human actions like /checklist clear that never produce a tool result. Size check: index.ts, the pi wiring, is 324 lines. store.ts and types.ts, about 640 lines, are plain TypeScript with no pi imports, testable with plain node.

Step 1: Give the model a tool. registerTool with a good description, prompt snippet and guidelines, and a before_agent_start hook to remind it of the current state on every prompt. Step 2: Give the human a view. A widget below the editor, a ☑ n/m footer, a /checklist command, and custom renderers so tool calls read like "checklist stg" instead of JSON. Step 3: Keep the state in the session. appendEntry for every change, and rebuild from getBranch() on session_start and session_tree. Then /resume, /tree, /fork and compaction all just work, and you never write a database. Step 4: Two of the three, side by side. speedometer only observes events; pi-checklist adds new abilities, new UI and its own state. The hollow stop is where we go next: context-prune, which changes what the model sees on every single request. Same extension API, escalating power. Size: index.ts, the pi wiring, is 324 lines, and the rules live in plain TypeScript with no pi imports. A minimal version with three tools, the hook, the append and the rebuild would be well under 300 lines. The same pattern works for anything the agent should track: a scratchpad, open questions, a test matrix. Try it: pi install npm:pi-checklist, or copy the pattern and write your own.
