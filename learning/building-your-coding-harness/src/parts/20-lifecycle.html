Part two. We've just seen the loop every coding harness runs: input, context, the model call, streaming, tool calls, tool results, and around again. Pi's key idea is that every one of those stages fires a named, typed event. An extension is just code that subscribes to those events. Some events only tell you what happened. Others let you return a value that changes what happens next. Those are the ones marked with a pencil throughout this section. By the end of this section you should recognise names like context, tool_call, message_update and before_agent_start when they show up in the three real extensions.

what is an extension?

One file. One function. It gets pi.

Step 0: An extension is a TypeScript file whose default export is a function. Pi calls that function once at load time and hands it the ExtensionAPI object, which we call pi. Step 1: The factory is where you wire everything up. Drop the file into ~/.pi/agent/extensions for global use, or .pi/extensions in a project (project-local ones load only once you trust the project). Type /reload and it's live. Step 2: pi.on subscribes to one of 36 typed lifecycle events. This handler runs on every turn_end. Step 3: registerTool gives the model a brand-new tool with a TypeBox schema and an execute function. You can even override built-ins like read or bash. Step 4: registerCommand adds a slash command with autocomplete. Step 5: and ctx, the second argument to every handler, gives you the UI: footer status, widgets, dialogs, even full custom TUI components. Accuracy note: this file stitches together the turn_end status-line, roll_dice tool and /hello command snippets from the research, trimmed with comments. It's illustrative, not one shipped example. No build step and no npm install are needed, because pi loads the file through jiti and aliases its own packages.

This is the same loop as the previous section, now with pi's real event names attached to each stage. Click through, and chips glow as they fire. Click any chip at any time to open its inspector: when it fires, its payload, and what it can return. Step 1, Input: session_start fired once when pi started. Each prompt then fires input (you can transform the text or swallow it entirely), before_agent_start (inject a message or change the system prompt for this run), then agent_start. Step 2, Context: turn_start, then context, which gets a deep copy of the messages right before every LLM call. Gotcha: on turn 0, turn_start actually fires BEFORE the user message's message_start and message_end. The official docs diagram draws it the other way round, but the source is clear. Step 3, Provider: before_provider_headers (mutate headers in place), before_provider_request (see or replace the exact provider payload), after_provider_response (status and headers). Step 4, Stream: message_start when the stream starts, a message_update for every thinking, text or tool-call delta, and message_end when it's final. message_end can replace the message before it's written to the session file. Step 5, Tool calls: tool_execution_start, then tool_call after argument validation and before execute. This is where you block things. tool_execution_update streams partial output. Tools run in parallel by default. Step 6, Tool results: tool_result can patch content, details or isError, chained like middleware. Then tool_execution_end, and each toolResult message gets its own message_start and message_end. Step 7: turn_end with the assistant message and all its tool results. There were tool calls, so we go round again. Step 8: turn 1 goes through context, provider and stream again, now including the tool results. This time the model just answers. Step 9: no tool calls, so the inner loop exits: turn_end, agent_end, and agent_settled once there's nothing left to retry or compact. Step 10: the amber chips are the ones where a return value changes behaviour. 14 of the 36 events work that way; eight of them are on this loop. Important: handlers run before the TUI renders the event, and before the message is persisted.

How does dispatch actually work? Every handler for an event runs one after another, in extension load order, and each one is awaited. Step 1: ext A just observes. It reads the event and returns undefined, so nothing changes. Most events, like message_update, turn_end and agent_end, are observe-only. Step 2: ext B intervenes. For context it returns an object with messages, and pi swaps that in. Here 12 messages become 7. The numbers are illustrative; this is what pi-context-prune does for real. Step 3: the result is chained. ext C receives B's version, not the original. context, tool_result and before_agent_start's systemPrompt all chain like this. tool_call is different: the first handler that returns block wins, and pi stops asking the rest. Step 4: pi uses the final value. For context it's a deep copy, so the session file on disk never changes. Step 5: gotcha. Handlers are awaited, so an expensive handler slows the whole loop. That includes message_update, which fires on every streamed delta. That's why speedometer throttles its footer updates. Step 6: failures are safe. A handler that throws is caught, reported, and the agent carries on. The one exception is tool_call, which has no try/catch in the runner: if your tool_call handler throws, that tool call becomes an error result. It fails closed, which is what you want from a guard.

Three quick demos of what a return value can do. First: a guard. Step 0: the model emits a bash tool call with rm -rf dist. Step 1: tool_call fires after the arguments are validated against the schema and before execute runs. We narrow with isToolCallEventType("bash", event). Checking event.toolName === "bash" doesn't narrow the TypeScript union, so the helper gives us a typed input with command and an optional timeout. Step 2: we return block true with a reason. The first handler to block wins. execute never runs, and tool_result does not fire for blocked calls; pi goes straight to tool_execution_end with an error. Step 3: the model receives the reason as an error tool result, so it can adapt, for example by asking you or trying a narrower command. Aside: you can also edit event.input in place to patch arguments rather than blocking. And pi deliberately ships without permission popups; the README says to build your own confirmation flow with extensions. The shipped examples permission-gate.ts and protected-paths.ts do exactly that.

This is every event pi v0.85.1 exposes: 36, from the on() overloads in the type definitions. You don't need to memorise them. The point is that nearly every boundary in the harness is covered. Click any chip for its details. Step 1, session: session_start fires on startup, reload, new, resume and fork. The session_before_* events can cancel the switch, fork, compaction or tree move, and session_before_compact can even supply your own summary. session_tree fires after /tree navigation, which is how extensions like checklist rebuild state for the new branch. Step 2, agent and turn: before_agent_start, agent_start, turn_start, turn_end, agent_end, and agent_settled when nothing is left to retry or compact. Step 3, message: start, update per delta, and end. message_end can replace a message before it's persisted. Step 4, tool: tool_execution_start, tool_call (block or patch), tool_execution_update, tool_result (patch), tool_execution_end. Step 5, provider and context: context rewrites messages; before_provider_headers mutates headers in place; before_provider_request can replace the payload; after_provider_response gives you status and headers. Step 6, input and startup: input can transform or swallow a prompt, user_bash can take over !commands, project_trust decides whether project-local extensions load, and resources_discover adds skill, prompt and theme paths. Step 7, model and UI: model_select, thinking_level_select, and ui_prompt_start and ui_prompt_end around dialogs. Step 8: the 14 whose return value changes behaviour. Two more change things by in-place mutation instead: before_provider_headers, and tool_call's event.input.

Why is pi so easy to extend? The README opens with: "Pi is a minimal terminal coding harness. Adapt pi to your workflows, not the other way around, without having to fork and modify pi internals." Step 1, minimal core: pi deliberately leaves things out. From the README: "No plan mode. Write plans to files, or build it with extensions, or install a package." The same goes for sub-agents and permission popups. Step 2, everything is an event: 36 typed events, and this isn't a bolted-on plugin layer. The core's own hook points, like beforeToolCall, afterToolCall, transformContext and onPayload, are the same seams extension events come from. Step 3, TypeScript with no build step. Quoting the docs: "Extensions are loaded via jiti, so TypeScript works without compilation." Pi aliases its own packages and typebox, so a single .ts file needs no npm install. Step 4, no fork: drop the file in ~/.pi/agent/extensions or a project's .pi/extensions. Step 5, hot reload: type /reload. It fires session_shutdown, re-imports everything with a fresh module cache, then session_start with reason reload. There's no file watcher; it's manual, but it's instant and you keep your session. Step 6, share it with pi install npm: or git:. Bonus: pi's docs start with "pi can create extensions. Ask it to build one for your use case." And a crashing handler is logged rather than killing the agent. One caution from the docs: "Extensions run with your full system permissions and can execute arbitrary code. Only install from sources you trust."

You now know enough to read any pi extension. Here are the three we'll dig into, and where each one plugs into the loop. They're deliberately in order of how much they change the harness: watch, then add, then rewrite. Step 1, pi-speedometer: pure observation, the smallest possible change. It starts a clock in before_provider_request without touching the payload, watches deltas in message_update, snaps to exact usage at message_end, and paints the footer with ctx.ui.setStatus. The pencil marks on those chips show what the event CAN do; speedometer only observes. Step 2, pi-checklist: one step further. Three new tools via registerTool, open tasks appended to the system prompt in before_agent_start, state saved with appendEntry into the session file, and rebuilt on session_start and session_tree so branches keep the right list. The agent gains an ability it didn't have. Step 3, pi-context-prune: the biggest change, so it goes last. It captures each batch of tool calls at turn_end, flushes summaries when an agent message ends (message_end), and rewrites the request in context so old tool results are replaced by summaries. It registers a context_tree_query tool so the model can pull any original back. It also uses session_start, session_tree and before_agent_start; we'll see those in the walkthrough. Step 4: three very different features, all built from the same small set of hooks you've just seen. Let's start with the lightest one, speedometer.
