pi-context-prune

Rewrite what the model sees on every request.
Keep the truth on disk.

The last extension, and the one that changes the most. Speedometer only watched the loop; checklist added a tool to it. This one reaches into the loop itself: it rewrites what the model sees on every single request, without touching the saved session, and it gives the model a tool to get things back. The picture on the right is the visual language for the next ten minutes: the context window as a stack of messages, height roughly proportional to tokens. Coral is tool output, green is a summary, violet is a tool call.

[Step 0] Here are the three raw tool results from our example: read, npm test, grep. About 11,000 tokens, illustrative. [Step 1] Once the task is done, a side LLM call (the summarizer) turns them into a short summary, roughly 270 tokens in total, with short refs t1, t2, t3 at the bottom. [Step 2] The originals aren't deleted. They're stored in the session as index entries, which pi never sends to the model. So "pruned" means "not in this request", not "gone". [Step 3] And because the summary lists refs, the model has an escape hatch: a tool called context_tree_query that fetches the full original back. Lossy summary, lossless recovery.

This is the whole extension mapped onto the lifecycle you just saw. The ✎ marks the hooks whose return value changes what pi does. [1] session_start and session_tree: on startup, reload or /tree navigation it reloads config and rebuilds its index from the current branch, so state is branch-aware. [2] before_agent_start: only in agentic-auto mode, it appends instructions to the system prompt telling the model when to call context_prune. [3] context: the important one. It runs before every LLM call and filters out tool results that are already summarized. It changes that one request only. [4] turn_end: after each turn with tool calls it captures a batch: the assistant text plus each call and its result. Nothing is summarized yet. [5] message_end: in the default agent-message mode, the first assistant message with no tool calls means the task is done, so it flushes. [6] A registered tool, context_tree_query, which is the recovery path. [7] A /pruner command with subcommands. Also, tool_execution_end triggers on-context-tag mode, agent_end only updates status, and a second tool, context_prune, exists for agentic-auto.

export function pruneMessages(messages, indexer) {
return messages.filter((msg) =>
!(msg.role === "toolResult" &&
indexer.isSummarized(msg.toolCallId)));
}

This is the slide that explains why the default mode batches instead of pruning eagerly. Token numbers are illustrative; the rewrite counts follow straight from the mode definitions. [0] The rule providers give us: a cache hit needs the earlier prompt prefix to be byte-identical. Append to the end and you keep the hit. Change something earlier and the provider recomputes from the point of the change onward, and pays to write that new prefix into the cache. That is exactly what pruning does: it edits earlier messages. The extension's README says it plainly: pruning too often saves in-context tokens while still hurting latency and cost. [1] every-turn flushes inside turn_end, after every tool-using turn. Four tasks of three tool turns means twelve rewrites and twelve summarizer calls, and pi awaits each one, so it sits in the critical path of the turn. Look at the pattern: the prefix is never left alone for more than one request, so the cache never earns anything back. The mode guidance in the code says exactly this: "Debugging only. Prunes after every tool turn, which is easiest to inspect but churns provider prompt caches the most." [2] agent-message, the default: flush once, on the first assistant message with no tool calls. One rewrite per task instead of one per turn. The request right after the flush is the one that pays, and it is the cheapest one to pay for, because it is the small pruned request: about 3,000 tokens instead of 14,000. Then the rest of that task appends on top of it and hits the cache every time. [3] Here is the part people miss. The summaries are not outside the cache. After the flush, the new, shorter prefix, summaries included, is what gets written to the cache, and those green blocks are then read from cache for the whole rest of the batch. [4] And it compounds. Each batch's floor sits higher than the last, because the summaries from earlier batches are already cached and never change again. So over a long horizon you are not fighting the cache, you are climbing a staircase: rewrite once, re-cache small, reuse for a whole batch, repeat. The cache builds up fine. That is the opposite of every-turn, which resets before the cache is worth anything. [5] So the guidance is: batch the prune. agent-message batches per task, on-context-tag per milestone, agentic-auto lets the model pick the boundary, and its system prompt says to aim at 8 to 12 related tool calls and warns that calling context_prune after every 2 or 3 hurts prompt-cache efficiency. Worth saying out loud: no pruning at all is perfectly cache-friendly, because it only ever appends. The reason we prune anyway is the other three costs from the problem slide: attention, the window, and re-reading a 30,000-token prefix on every single request.

Quick tour; one click per card. [1] If the wrapped summary has more characters than the raw results, the batch is skipped: no summary, no index entry, raw results stay. The frontier still advances with outcome skipped-oversized, so it isn't retried forever. Our example: about 720 chars versus 36,000. [2] If the summarizer call fails (auth, unknown model, provider error) you get a toast, the batches are restored to pending, and the frontier doesn't advance. Cancelling with Esc in agentic-auto behaves the same, without the error toast. [3] All state (index, stats, frontier) is rebuilt from sessionManager.getBranch() on session_start and session_tree. If you navigate back to before a prune, those IDs aren't indexed on that branch, so the raw results come back automatically. [4] DEFAULT_CONFIG.enabled is false, so you opt in with /pruner on. Settings live in ~/.pi/agent/context-prune/settings.json. [5] Prefix cache: three separate pieces of care. The default mode rewrites once per task; the context hook returns undefined when nothing changed, so an unchanged request is sent untouched; and the agentic-auto pruner-note is appended to the last tool result only, never persisted, so only the tail of the prefix moves. [6] Short refs like t1 are stored in the summary's details, so after a restart the aliases are re-registered and numbering continues from the max.
