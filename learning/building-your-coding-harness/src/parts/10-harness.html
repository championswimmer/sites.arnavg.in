What a harness does

First stop: what a coding harness actually is. When we say "Claude Code is good" or "Cursor feels fast", we usually mean the model, but a large part of that experience comes from the program wrapped around the model. pi describes itself exactly this way: "Pi is a minimal terminal coding harness." Its default system prompt even tells the model it is "operating inside pi, a coding agent harness." Over the next few slides: what the model can and can't do on its own, the loop that turns it into an agent, the layers pi is built from, and why the same model feels different in different harnesses.

Step 0: Strip away the product and a language model is a function: text in, text out. It doesn't keep state between calls. Everything it "knows" about your conversation has to be in the text you send it. Step 1: Say we ask it to fix a failing login test. Step 2: The model can't read login.ts, it can't run npm test, and it doesn't remember the previous request. Each call starts from zero. Step 3: What a tool-using model can do is reply with a structured request: "please call the bash tool with command npm test". In pi, the provider layer normalises this into a toolCall block in the assistant message, whichever provider you use. The exact shape on the slide is simplified. Step 4: Some program has to see that request, actually run the command, paste the output back into the conversation, and call the model again. That program is the harness. One task: fix the failing login test

You type one line.

The harness builds the context: instructions, tools, history.

It sends all of it to the model.

The model streams back text and a tool call.

The harness runs npm test. The model can't.

The output joins the context. Loop.

Turn 2: the model asks to read login.ts.

Turn 3: it asks to edit it.

Turn 4: plain text, no tool calls…

…so the loop ends. One prompt, four model calls.

This is the core of every coding agent. The task: "fix the failing login test". The file names, test output and the fix itself are illustrative, and the size bar has no real numbers. The loop structure is pi's real code path. Step 1 (Input): you type one line. pi first checks for built-in and extension slash commands, expands skills and prompt templates, then builds the user message. Step 2 (Context): the harness assembles what the model sees. The system prompt comes from buildSystemPrompt: tool snippets, guidelines, AGENTS.md context files, skills, the cwd. Then the tool definitions and the message history. The model knows only what is in this stack. Step 3 (Provider): pi-ai turns that provider-neutral context into an HTTP request for Anthropic, OpenAI, Google, Bedrock or others. Note the label on the right: the whole stack is sent on every call, not just the new message. Step 4 (Stream): the answer streams back as normalised events: text deltas, thinking deltas, tool-call deltas. Here it says it will run the tests and emits a tool call for bash. Step 5 (Tool calls): the harness looks up the tool, validates the arguments against its schema, and runs it. pi runs multiple tool calls in parallel by default. Step 6 (Tool results): the output is wrapped as a toolResult message and appended. Because there were tool calls, the loop goes back to Context and calls the model again. Steps 7–8: two more laps: read the file, then edit it. Watch the context stack: the test log and the whole file are still in there, and they are re-sent on every later call. Hold that thought; the context-prune extension later in the talk deals with exactly this. Step 9–10: the model replies with plain text and no tool calls, so the inner loop exits and the run is done. Between laps pi can also auto-compact if the context gets too big, and after the run it may retry an error. One prompt from you, four model calls, three tool runs, all driven by the harness. Demo tip: the "auto-play loop" button steps through the whole loop on a timer; click it again to pause.

The model

the only part you don't build

pi is split into npm packages, and each one is a layer of the harness. We'll light them from the bottom up. Step 1, pi-ai: the provider abstraction. It takes a provider-neutral context (system prompt, messages, tools), builds the Anthropic, OpenAI, Google or Bedrock request, and streams back one normalised event shape: text, thinking and tool-call deltas, then done or error. Nothing above this layer sees provider wire formats. Step 2, pi-agent-core: the generic agent loop from the previous slide. Stream the assistant message, run the tool calls, append the results, repeat. It has no UI and knows nothing about coding. Step 3, pi-coding-agent's AgentSession: this turns the generic loop into a coding agent. It adds the coding tools, JSONL session files that store a branching tree, compaction, retries, the system prompt, and the extension runner. By default the model gets four tools: read, bash, edit and write. grep, find and ls exist but are off by default. Step 4, the terminal UI: renders the transcript, the editor, the footer and widgets, and handles built-in slash commands. The same AgentSession also runs without the TUI in print mode, RPC mode, or embedded through the SDK. Step 5: all four layers are the harness. The model sits outside, at the end of an HTTP call. It is the one piece you rent rather than build.

Same weights. Different agent.

Everyone compares models. Very few people compare harnesses, but the harness sets most of these dials. Both columns here send requests to the same model. Dial 1, context: by default pi keeps every tool output in context until compaction summarises the older part. With the context-prune extension, outputs from a finished task are swapped for short summaries in the model's view, while the originals stay in the session. Dial 2, tools: pi's defaults are read, bash, edit and write. An extension can register new tools, like the checklist extension's three tools, or block a call such as rm -rf before it runs. Dial 3, stopping: by default the loop ends when the model replies without tool calls. A tool can also return terminate to end the run. Dial 4, what you see: the TUI shows the transcript, editor and footer. Extensions can paint the footer and widgets: speedometer shows tokens per second, and checklist shows task progress. Dial 5, what's saved: pi writes a JSONL session file shaped like a tree, and extensions can store their own state entries in that same file. Step 6: nothing about the model changed. Every difference in the right column is harness code, and each one is a real extension you'll see later in this talk.

This is the line from pi's README that sums up the design: "Pi is a minimal terminal coding harness. Adapt pi to your workflows, not the other way around, without having to fork and modify pi internals." pi leaves features out on purpose. The README says it "skips features like sub agents and plan mode" and suggests building them with extensions or installing a package instead. There are no permission popups either; you build your own confirmation flow if you want one. Step 1: here is the loop we just walked through, flattened: Input, Context, Provider, Stream, Tool calls, Tool results, Done. Step 2: the reason pi can stay minimal is that every one of these boundaries is an event. An extension, just a TypeScript file, can observe it, and at many of them it can change what happens next. pi's own core wires its behaviour through the same seams, so extensions aren't a bolted-on plugin layer.
