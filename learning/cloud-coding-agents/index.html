03 / Pause & resume

Don't kill it.
Freeze it.

Snapshots turn idle RAM into cheap storage.

ZZZ
Stop three: the first fix. Instead of killing idle VMs and losing everything, or paying to keep them warm, we freeze them: capture their state into snapshots on cheap storage, release the CPU and RAM, and thaw them back in about a second when the human returns.

state has two layers

Freeze both halves

🧠 Execution state

RAM + CPU + device state

memory file + state file

thawed on demand, page by page

💾 Filesystem state

writable disk / overlay

block snapshot → object store

only changed blocks travel

Two clicks. Execution state is RAM plus CPU and device state — Firecracker writes it as a memory file plus a state file, and on restore pages fault back in on demand. Filesystem state is the writable disk or overlay — snapshotted to block storage, then tiered to object storage. Because the base image is shared, only changed blocks travel. Pause means capturing both, then paying storage-only while idle.

The lifecycle in four clicks. Running bills CPU and RAM. Pause writes the memory file, state file and disk delta to storage and frees the host — try the pause button, the card freezes. Parked state costs storage pennies. Resume mmaps the memory file and faults pages in on demand — try resume, it wakes in about a second. Caveat for the Q&A: vsock resets across restore, so network handles must be re-established.

why microVMs — Firecracker numbers

Built for thousands

<125msboot a new microVM
<5MiBVMM overhead each
~1ssnapshot resume

Firecracker was built for exactly this density.

A fresh microVM boots in under 125 milliseconds.

Each one costs under 5 MiB of host overhead.

Resume faults pages in on demand — about a second, even for thousands parked.

Why microVMs and not plain containers or full VMs. Firecracker's advertised numbers: under 125 milliseconds to boot, under 5 megabytes of VMM overhead per VM, snapshot restore around a second via mmap plus userfaultfd on-demand paging. Alternatives exist — Kata template cloning for density, gVisor where KVM is unavailable, CRIU for process-level checkpoint — but for thousands of pausable agent VMs, Firecracker-style snapshots are the reference design. Keep hot snapshots on local NVMe, tier cold ones to object storage.

Stop four: the second fix. Workplace code is often one giant monorepo — tens of gigs. Copying it per session is slow and wasteful, and most sessions barely touch it. So keep one warm checkout on the dev server, hot in page cache, and give each session an instant copy-on-write view. Only changed blocks cost anything.

Two clicks. Naive: two thousand full clones of a forty-gig monorepo is eighty terabytes moved and stored — so each agent can change three files. Copy-on-write: a clone is metadata pointing at the same blocks, near-zero cost until a session actually writes. Reads are free and shared; writes pay per changed block.

The heart of the talk — let the audience click. The warm copy is one checkout on the dev server's fast SSD, hot in page cache. Each session view is metadata pointing at the same blocks: instant, near-zero bytes. When session A edits auth.ts, only that file copies up into its private layer — the rest stays shared. Session B changed nothing and pays nothing, and unmodified files share the host page cache, so two thousand sessions don't need two thousand copies in RAM either. Implementation notes for Q&A: OverlayFS merges a shared lowerdir with a private upperdir per session; ZFS or btrfs clones do it at block level; expose into the microVM via virtiofs.

Spell out the literal mechanism. Reads are served from the shared base — zero cost. The first write to a file copies just that file into the private upper layer; deletions become whiteout markers. The buttons compare implementations: OverlayFS is ubiquitous and file-granular, great for read-mostly repos; ZFS clones share at block level with native snapshots — better for heavy writes, costs running ZFS; btrfs gives the Linux-native middle ground. And pause composes with this: the per-session writable layer is exactly what gets snapshotted to block storage.

Six APIs, two shapes.

RAM-preserving: E2B and Daytona pause the live VM — memory included.

Snapshot-restart: the rest restore the filesystem into a fresh session.

Railway: checkpoint/fork per environment — app-adjacent workers, not thousands of agent VMs.

Let the audience click cards; details appear below. Step 1 lights up the two RAM-preserving picks: E2B's pause saves filesystem plus memory by default with about-a-second resume, paused free; Daytona VM sandboxes preserve memory on pause, filesystem on stop, parked VMs bill disk only. Step 2 covers snapshot-restart: Fly suspends via Firecracker snapshots in hundreds of milliseconds but discourages huge or mass suspends; Vercel stop auto-snapshots the filesystem with tiered timeouts; Cloudflare backs up to R2 with a 3-day default TTL; Modal snapshots become restorable clones with a 7-day TTL. Step 3: Railway checkpoints and forks whole sandboxes per environment — fine for ephemeral workers, not the thousands-of-pausable-VMs shape.

Two clicks. While running, everyone meters CPU plus RAM per second, plus creations and egress — that is the same everywhere. While parked, the bill collapses: E2B paused sandboxes are free, Daytona and Fly charge disk only, Vercel, Cloudflare and Modal charge snapshot or backup storage. That collapse is the whole business case: the waiting money from section two goes nearly to zero.
