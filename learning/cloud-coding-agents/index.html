Each step needs tools, state and the right permissions.

Plan: read the ticket and inspect the repo.

Act: edit files, run commands and call tools.

Observe: read logs, exit codes and CI results.

Repair: reproduce the failure, fix it and run again.

Handoff: open a PR and link the ticket. Deploy with approval.

Give each step only the access it needs.

Walk through the five steps. The harness runs locally; models and remote tools may live elsewhere. Separate local file writes from permission to push to GitHub. Cloning only needs read access. Debug against staging or scrubbed test data. A passing test does not grant permission to deploy.

03 / Pause & resume

Pause it.
Don't kill it.

Save the state. Release the CPU and RAM.

ZZZ
Save the VM state to storage, then release its CPU and RAM. Restoring a small VM can take around a second. Timing depends on the platform, memory size and storage.

Execution state includes memory, CPU registers and device state. Firecracker saves memory and VM state separately. The platform must snapshot the disk too, at a consistent point in time. Lazy paging can speed up restore. Incremental disk snapshots avoid copying unchanged blocks.

Running uses CPU and RAM. Pausing saves state and releases those resources. Resume restores that state rather than starting the app again. The buttons illustrate this; they do not control a real VM. Existing network connections may need to reconnect after restore. Resume time is not a fixed SLA.

Firecracker advertises fast boot and low VMM overhead. Guest RAM and application startup are extra. The one-second restore figure is an example for small VMs, not a Firecracker guarantee. Local NVMe helps with hot snapshots; object storage can hold colder ones.

A large monorepo can take tens of gigabytes. Most tasks change only a small part of it. Keep an immutable base checkout on each host and give sessions copy-on-write views. Each session still needs compute and private state, but it need not duplicate the whole repo.

Two thousand 40-GiB checkouts occupy 80,000 GiB, or about 78 TiB, before compression or deduplication. A copy-on-write clone initially shares the base data. It adds metadata, then private data as the session writes. This saves duplicate storage. It does not make reads or compute free.

Each chat still gets a microVM. What changes is the storage underneath it. The host shares an immutable base; each VM gets a private writable disk view. Block-level clones can back virtio-blk devices. OverlayFS is a file-level alternative, not itself a VM disk device. Upstream Firecracker does not support virtiofs. Do not assume host storage sharing also deduplicates guest RAM. Size the fleet for active CPU and memory, not just the number of stored sessions.

This example restores files, not running processes.

Snapshots are just files in object storage.

A read-only base plus a writable layer keeps edits separate.

A backup stores a directory archive and metadata in R2. Restore fetches them and adds a writable layer. That is slower than keeping a live local disk, but it survives the container being replaced. A Durable Object coordinates the sandbox and can persist session metadata. Applications must choose what to save.

A cloud agent is a dev machine you return to. A sandbox is a workspace for one task. Both can use prepared disk state. Neither disk checkpoints nor sleep preserve running processes. read the bill in two parts

Stopping compute is not always a $0 bill

While running

  • CPU: used or allocated, by provider
  • RAM: often provisioned capacity
  • Disk, network and creation fees may apply
  • Model tokens are a separate cost

After stopping

  • Pause can end compute charges
  • Snapshots, disks and backups may still bill
  • Retention limits affect how long state survives
  • Delete state only after saving the result
Providers meter resources differently. Do not assume every service bills only actual CPU and RAM use. Pausing reduces compute cost, but retained state can still have a bill and an expiry date. Check both before leaving hundreds of sessions idle.
