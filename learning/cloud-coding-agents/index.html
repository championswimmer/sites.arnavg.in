Welcome. You all use coding agents. This talk is about the half nobody sees: the machine each agent lives on. I will show you what the agent does with that machine, why one VM per chat goes broke at workplace scale, and the two tricks that fix it: pausing VMs into snapshots, and sharing one repo with copy-on-write. 03 / Pause & resume

Pause it.
Don't kill it.

Idle RAM becomes cheap stored snapshots.

ZZZ
Stop three: the first fix. Instead of killing idle VMs and losing everything, or paying to keep them warm, we freeze them: capture their state into snapshots on cheap storage, release the CPU and RAM, and thaw them back in about a second when the human returns.

state has two layers

Freeze both halves

🧠 Execution state

RAM + CPU + device state

memory file + state file

thawed on demand, page by page

💾 Filesystem state

writable disk / overlay

block snapshot → object store

only changed blocks travel

Two clicks. Execution state is RAM plus CPU and device state — Firecracker writes it as a memory file plus a state file, and on restore pages fault back in on demand. Filesystem state is the writable disk or overlay — snapshotted to block storage, then tiered to object storage. Because the base image is shared, only changed blocks travel. Pause means capturing both, then paying storage-only while idle.

The lifecycle in four clicks. Running bills CPU and RAM. Pause writes the memory file, state file and disk delta to storage and frees the host — try the pause button, the card freezes. Parked state costs storage pennies. Resume maps the memory file back and faults pages in on demand — try resume; small agent VMs typically wake in about a second (restore time grows with memory and vCPUs, no official SLA). Caveat for the Q&A: vsock resets across restore, so network handles must be re-established.

Firecracker was built for exactly this density.

A fresh microVM boots in under 125 milliseconds.

Each one costs under 5 MiB of host overhead.

Resume faults pages in on demand. About a second for small agent VMs — restore time grows with VM size.

* Firecracker publishes boot ≤125 ms and ≤5 MiB overhead; restore speed is workload-dependent.

Why microVMs and not plain containers or full VMs. Firecracker's advertised numbers: under 125 milliseconds to boot, under 5 megabytes of VMM overhead per VM, snapshot restore around a second via mmap plus userfaultfd on-demand paging. Alternatives exist — Kata template cloning for density, gVisor where KVM is unavailable, CRIU for process-level checkpoint — but for thousands of pausable agent VMs, Firecracker-style snapshots are the reference design. Keep hot snapshots on local NVMe, tier cold ones to object storage.

Stop four: the second fix. Workplace code is often one giant monorepo — tens of gigs. Copying it per session is slow and wasteful, and most sessions barely touch it. So run a few beefy devservers, each holding one warm checkout — hot in page cache, outside any VM — and start one microVM per user chat inside the devserver. Each microVM forks a copy-on-write view of that warm clone. Only changed blocks cost anything.

Two clicks. Naive: two thousand full clones of a forty-gig monorepo is eighty terabytes moved and stored — so each agent can change three files. Copy-on-write: a clone is metadata pointing at the same blocks, near-zero cost until a session actually writes. Reads are free and shared; writes pay per changed block.

The heart of the talk — let the audience click the microVMs. There is no VM per chat floating in the cloud: there are a few beefy devservers, and each one holds a single warm clone of the monorepo on its fast SSD, outside every VM, hot in the host page cache. Each user chat starts a microVM inside a devserver, and that microVM forks a copy-on-write view of the warm clone — metadata pointing at the same blocks, instant, near-zero bytes. When chat A edits auth.ts, only that file copies up into its private layer. Chats B and C changed nothing and pay nothing — and unmodified files share the host page cache, so hundreds of chats on one box do not need hundreds of copies in RAM either. Implementation notes for Q&A: on the host, OverlayFS merges the shared lowerdir with a private upperdir per microVM, or ZFS hands each one a writable block-level clone of a snapshot — either way each microVM gets its CoW view attached as its own virtio-blk disk. (Honest footnote: upstream Firecracker has no virtiofs support, so the sharing happens at the block layer, not as a shared folder.)

Spell out the literal mechanism. Reads are served from the shared base — zero cost. The first write to a file copies just that file into the private upper layer; deletions become whiteout markers. The buttons compare implementations: OverlayFS is ubiquitous and file-granular, great for read-mostly repos; ZFS clones share at block level with native snapshots — better for heavy writes, costs running ZFS; btrfs snapshots subvolumes with extent-level sharing, the Linux-native middle ground. And pause composes with this: pausing captures two things together — the microVM's memory and device state in one snapshot file, and the per-session writable layer as a disk snapshot. Firecracker manages the disk side separately, so a platform snapshots both and restores both.

Stop five: the technology layer. Forget brand names for a minute. Three ideas, every platform.

Snapshots are just files in object storage.

Repos are shared with copy-on-write, same as section 4.

Each sandbox gets one owner that outlives its container.

Walk the three clicks using Cloudflare as the concrete example. One: object storage. A backup is a directory compressed to squashfs, uploaded to R2 next to a small metadata file. Restoring downloads both and mounts the archive read-only with a writable layer on top. It runs at object-storage speed, not disk speed — that is the honest trade. Two: shared files. That read-only mount plus writable upper layer is overlayfs — the same lowerdir/upperdir shape from section four. The industry keeps rediscovering copy-on-write. Three: one owner. A Durable Object is a single-threaded coordinator with private transactional storage — SQLite, key-value, alarms that wake it later. The container is disposable; the owner remembers. That split is what lets a sandbox sleep for hours and still know what it was doing.
