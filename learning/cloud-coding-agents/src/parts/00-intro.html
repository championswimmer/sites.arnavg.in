a talk about where coding agents really run

Why your coding agent needs a cloud

The computer behind the chat.

shell repo tests MCP tools
Welcome. You all use coding agents. This talk is about the half nobody sees: the machine each agent lives on. I will show you what the agent does with that machine, why one VM per chat goes broke at workplace scale, and the two tricks that fix it: pausing VMs into snapshots, and sharing one repo with copy-on-write. 3

you can start sessions from mobile that arrive with your repo cloned, tickets linked and can deploy to prod

Question 2 drops most of the room: staying connected to that same session from your phone, with Claude or Codex mobile, while it keeps running on your laptop. (Expect fewer hands here.) Question 3 should leave almost nobody: starting sessions from mobile that begin with your repo already cloned, have access to tickets, and can deploy to prod. (Expect almost nobody.) That funnel is the talk. We know agents work. We barely run them in the cloud. And almost nobody has them wired into work yet. Today is about closing those two gaps.

Six stops. First, what an agent session actually does with its machine — the loop, running code, tools, and why it must verify by running things. Second, the bill: what thousands of always-on VMs cost and where the money really burns. Third, the two fixes: pause VMs into snapshots and resume in a second, and share one warm repo with copy-on-write. Fourth, the three ideas underneath every platform. Fifth, where to run it: try it on a side project first, then six hosted options. Sixth, the whole system on one slide for Q&A.
