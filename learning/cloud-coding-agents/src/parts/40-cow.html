Stop four: the second fix. Workplace code is often one giant monorepo — tens of gigs. Copying it per session is slow and wasteful, and most sessions barely touch it. So run a few beefy devservers, each holding one warm checkout — hot in page cache, outside any VM — and start one microVM per user chat inside the devserver. Each microVM forks a copy-on-write view of that warm clone. Only changed blocks cost anything.

Two clicks. Naive: two thousand full clones of a forty-gig monorepo is eighty terabytes moved and stored — so each agent can change three files. Copy-on-write: a clone is metadata pointing at the same blocks, near-zero cost until a session actually writes. Reads are free and shared; writes pay per changed block.

A devserver, not a VM per chat. Watch it fill up.

One warm clone sits on the devserver's SSD — outside every microVM, hot in page cache.

Each chat starts a microVM that forks a CoW view: metadata only, ~0 bytes, instant.

A writes auth.ts → only that file copies up into its private layer. The rest stays shared.

B and C changed nothing → still pay nothing. Unmodified files share the host page cache too.

The heart of the talk — let the audience click the microVMs. There is no VM per chat floating in the cloud: there are a few beefy devservers, and each one holds a single warm clone of the monorepo on its fast SSD, outside every VM, hot in the host page cache. Each user chat starts a microVM inside a devserver, and that microVM forks a copy-on-write view of the warm clone — metadata pointing at the same blocks, instant, near-zero bytes. When chat A edits auth.ts, only that file copies up into its private layer. Chats B and C changed nothing and pay nothing — and unmodified files share the host page cache, so hundreds of chats on one box do not need hundreds of copies in RAM either. Implementation notes for Q&A: on the host, OverlayFS merges the shared lowerdir with a private upperdir per microVM, or ZFS hands each one a writable block-level clone of a snapshot — either way each microVM gets its CoW view attached as its own virtio-blk disk. (Honest footnote: upstream Firecracker has no virtiofs support, so the sharing happens at the block layer, not as a shared folder.)

Spell out the literal mechanism. Reads are served from the shared base — zero cost. The first write to a file copies just that file into the private upper layer; deletions become whiteout markers. The buttons compare implementations: OverlayFS is ubiquitous and file-granular, great for read-mostly repos; ZFS clones share at block level with native snapshots — better for heavy writes, costs running ZFS; btrfs snapshots subvolumes with extent-level sharing, the Linux-native middle ground. And pause composes with this: pausing captures two things together — the microVM's memory and device state in one snapshot file, and the per-session writable layer as a disk snapshot. Firecracker manages the disk side separately, so a platform snapshots both and restores both.
