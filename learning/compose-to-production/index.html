The gap

5 min

Compose answers exactly one question: given a machine that already has Docker on it, which containers run and how do they reach each other. Every other question in production belongs to somebody else.

When you run docker compose up -d on a VPS, you are silently relying on a long list of things having already happened. The machine exists. It has a public IP and a disk. A firewall lets 443 in. DNS points at it. Docker is installed and starts on boot. And when you ship new code, a human SSHes in and runs git pull && docker compose up -d.

In production each of those becomes a job with an owner. The four tools in this course are four different owners, and the cleanest way to keep them straight is to ask which question each one answers.

The questionThe owner
Does this machine, network, database, cluster or DNS record exist at all?Terraform
Given a machine that exists, is the software on it installed and configured the way we want?Ansible
What does one deployable unit of our app look like, expressed once and parameterised per environment?Helm
Does the live cluster currently match what is in Git — and if not, make it match.Argo CD

Two of these are infrastructure, two are applications

The single most useful split. Terraform and Ansible are concerned with the substrate: the cloud account, the machines, the managed services, the operating systems. They run before your app exists, and they run again only when the substrate changes — which might be once a month.

Helm and Argo CD are concerned with the application: the containers, their config, their versions, their rollouts. They run every time an engineer merges a pull request — which might be forty times a day.

That difference in cadence is why the tools are separate. Anything that changes forty times a day should not be described in the same place as your VPC.

Terraform
Managed services & machinesRDS Postgres, ElastiCache Redis, MSK Kafka, S3 buckets, the EKS cluster itself, bare EC2 instances

The shape of the appDeployments, Services, Ingress, HPA, ConfigMaps — templated once, valued per environment

Getting that shape into the cluster, continuouslywatching Git, syncing, detecting drift, healing, rolling back

Helm and Argo CD are not alternatives

This trips almost everybody up. Helm is a packaging and templating format — it turns values into Kubernetes YAML. Argo CD is a delivery mechanism — it takes Kubernetes YAML and keeps it applied to a cluster. Argo CD renders your Helm chart itself and then applies the result. They are a pipeline, not a choice.

You probably don’t need all four

A small team on EKS with fully managed data services can run Terraform plus Argo CD and never install Ansible, because there are no machines to configure — the nodes are cattle from an AMI. Ansible earns its place the moment you own a pet VM. In this course the ClickHouse cluster is that pet, deliberately, so you can see where the line falls.

urlshort — production topology one AWS account, one region

One box has two owners. The ClickHouse instances are created by Terraform and made into a ClickHouse cluster by Ansible. The load balancer is subtler still: Terraform sets up the controller and tags the subnets, but the actual ALB is created on demand from the Ingress object your chart defines. Shared ownership is normal — what matters is that only one tool writes each specific attribute.

Terraform

13 min

Terraform’s job is to make things exist. You describe the cloud resources you want in a file; it works out the difference between that file and reality, and calls the cloud’s API until they match.

You could do all of this with the AWS console, or with a long shell script full of aws rds create-db-instance calls. Terraform is different from the script in four specific ways, and all four are worth understanding before you write a line of it.

1. It is declarative, and it has a memory

A shell script says create a database. Run it twice, get two databases. Terraform config says a database with these properties exists. Run it twice, the second run does nothing.

That only works because Terraform keeps a state file: a JSON map from the addresses in your config (aws_db_instance.canonical) to real resource IDs in the cloud (db-XKPQ2N…), plus a snapshot of every attribute as it was at the last apply. State is what lets it tell “this is new” from “this exists and changed” from “this exists and is fine”.

The state file is the whole game

Almost every Terraform horror story is a state story. If the state is lost, Terraform thinks nothing exists and tries to create a duplicate of your production database. If two engineers apply at once, they write conflicting states and one set of changes silently vanishes. So the state never lives on a laptop: it lives in an S3 bucket (or Terraform Cloud, or GCS) with versioning on and locking enabled, from the very first commit.

infra/prod/versions.tf
terraform {
  required_version = "~> 1.10"

  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.60" }
  }

  # Remote state, encrypted, versioned, locked. Do this on day one --
  # migrating a local state file later is the worst afternoon of your quarter.
  backend "s3" {
    bucket       = "urlshort-tfstate"
    key          = "prod/infra.tfstate"
    region       = "ap-south-1"
    encrypt      = true
    use_lockfile = true   # native S3 locking; the old way was a DynamoDB table
  }
}

provider "aws" {
  region = "ap-south-1"
  default_tags {
    tags = { service = "urlshort", env = "prod", managed_by = "terraform" }
  }
}

2. It plans before it touches anything

terraform plan reads your config, refreshes the real state of each tracked resource, and prints the exact set of API calls it intends to make. Four symbols carry all the meaning:

  • + create — the resource is in your config but not in state.
  • ~ update in place — an attribute changed and the API can change it live.
  • - destroy — the resource is in state but no longer in your config.
  • -/+ replace — an attribute changed that the API cannot change live, so Terraform will delete the resource and create a new one. On a database, this is a production incident wearing a plus sign.

Reading plans carefully is the actual skill. Try it below: change something, plan it, and watch for the line that says forces replacement.

terraform plan

Try the rename toggle. Changing an RDS instance’s identifier is not an in‑place operation, so Terraform proposes deleting your database and building an empty one. Nothing warns you louder than that -/+, and nothing is easier to scroll past at 6pm.

3. The order of operations is derived, not written

Notice that you never told Terraform to create the subnet group before the database. It builds a dependency graph from the references in your code: the moment aws_db_instance.canonical mentions aws_db_subnet_group.private.name, an edge exists. Everything unrelated is created in parallel, which is why the apply above finished the EBS volumes while RDS was still churning.

You only reach for depends_on when the dependency is real but invisible to the code — an IAM policy that must be attached before a service can assume the role, for instance.

4. One language, many APIs

Providers are plugins that translate Terraform resources into API calls. AWS, Cloudflare, GitHub, Datadog, PagerDuty, your DNS registrar. The useful consequence: the DNS record pointing at the load balancer, the Datadog monitor watching it, and the GitHub repo secret holding the deploy role ARN can all be described in the same file as the load balancer, and they can all reference each other.

Note what is missing

Terraform attaches a 2 TB disk to each box and stops. It does not format it, mount it, install ClickHouse, or write config.d/cluster.xml. There is no user_data bash script either — that would run exactly once, at first boot, with no way to converge the box later. Everything from “an Ubuntu machine exists” to “a ClickHouse shard is serving” is the next module’s job.

Getting values out of Terraform

Outputs are the published interface of your infrastructure. Everything downstream — Ansible, Helm, your CI — reads these rather than hardcoding endpoints.

infra/prod/outputs.tf
output "redis_endpoint" {
  value = aws_elasticache_replication_group.cache.primary_endpoint_address
}

output "kafka_brokers" {
  value = aws_msk_cluster.events.bootstrap_brokers_sasl_iam
}

output "pg_secret_arn" {
  # the ARN, not the password. External Secrets will resolve it in-cluster.
  value = aws_db_instance.canonical.master_user_secret[0].secret_arn
}

output "eks_cluster_name" {
  value = module.eks.cluster_name
}

Endpoints are not secrets, so they can be committed straight into your Helm values for that environment. Credentials are, so only the ARN travels — the actual password is fetched inside the cluster at runtime. We will close that loop in module 4.

How to lay it out

Two conventions carry most teams a long way:

  • A directory per environment, each with its own backend key: infra/dev, infra/staging, infra/prod. Shared logic lives in modules/ and is called from all three. Terraform workspaces look like a neater answer but they share one config, so “prod has an extra read replica” turns into conditionals scattered through your code.
  • Split state by blast radius and cadence. The VPC changes twice a year; the EKS node groups change monthly. Keeping them in separate state files means a mistake in one cannot propose destroying the other, and a plan takes twenty seconds instead of four minutes.

Don’t deploy your app with Terraform

The helm_release resource exists and it is tempting. But then a release version lives in your infra state, every app deploy needs infra credentials, a failed rollout leaves state tainted, and you have no drift detection between deploys. Use it for cluster add‑ons that must exist before anything else — a CNI, cert‑manager, Argo CD itself — and nothing you ship weekly.

Do put the bootstrap in Terraform

Something has to install Argo CD before Argo CD can install things. Terraform creating the cluster and then applying exactly one Helm release — Argo CD — plus one root Application, is the clean version of that chicken‑and‑egg. After that, Terraform never touches the cluster’s contents again.

Ansible

10 min

Terraform handed you three Ubuntu boxes with an unformatted 2 TB disk bolted on. Ansible’s job is to turn those into a ClickHouse cluster, and to be able to do it again next month without breaking anything.

Mechanically it is simple: Ansible opens an SSH connection to each host, copies small Python programs over, runs them, collects the results, moves to the next task. No agent, no daemon, no server. If you can SSH to a box you can Ansible it.

Three nouns and you have the whole model:

  • Inventory — which hosts exist and what groups they are in.
  • Playbook — an ordered list of tasks to run against a group.
  • Module — the verb a task uses: apt, template, mount, systemd, user. There are thousands.

The property that makes it not a shell script

A task does not say “run apt install clickhouse-server”. It says “the package clickhouse-server at version 24.8 is present”. The module checks first, acts only if needed, and reports back one of three words:

  • ok — reality already matched. Nothing was done.
  • changed — reality did not match, and the module fixed it.
  • failed — it could not.

That distinction is the entire point of Ansible, and it gives you a genuinely useful property: a second run of a correct playbook should report zero changes. A playbook that keeps reporting changes on every run is a playbook with a bug — usually a shell: task someone reached for instead of a module.

Run the playbook below twice and watch the recap line.

ansible-playbook -i inventory/aws_ec2.yml site.yml

The third button is the interesting one. An engineer SSHes into clickhouse-02 at 3am to bump a setting and never writes it down. Run the playbook again: exactly one task reports changed on exactly one host, the file goes back to what the repo says, and the restart handler fires only there. Convergence, not a rerun of everything.

Handlers: restart only when something actually changed

Restarting ClickHouse on every run would be an outage generator. Handlers solve this: a task notifies a handler, and the handler runs once, at the end of the play, only if at least one notifying task reported changed.

roles/clickhouse/tasks/main.yml
- name: Install clickhouse-server
  ansible.builtin.apt:
    name: "clickhouse-server={{ clickhouse_version }}*"
    state: present
    update_cache: true
  notify: restart clickhouse

- name: Create filesystem on the data volume
  community.general.filesystem:
    fstype: ext4
    dev: /dev/xvdf

- name: Mount the data volume
  ansible.posix.mount:
    path: /var/lib/clickhouse
    src: /dev/xvdf
    fstype: ext4
    opts: noatime
    state: mounted

- name: Render cluster topology
  ansible.builtin.template:
    src: cluster.xml.j2
    dest: /etc/clickhouse-server/config.d/cluster.xml
    owner: clickhouse
    group: clickhouse
    mode: "0640"
  notify: restart clickhouse

- name: Ensure clickhouse-server is running and enabled
  ansible.builtin.systemd_service:
    name: clickhouse-server
    state: started
    enabled: true

- name: Create the analytics database
  ansible.builtin.command:
    cmd: clickhouse-client --query "CREATE DATABASE IF NOT EXISTS analytics"
  register: db_create
  changed_when: false   # the IF NOT EXISTS makes this safe, so don't lie about it
  run_once: true
roles/clickhouse/handlers/main.yml
- name: restart clickhouse
  ansible.builtin.systemd_service:
    name: clickhouse-server
    state: restarted
  # one host at a time, so the cluster never loses quorum mid-play
  throttle: 1

Variables and templates

The config file each host gets is generated from a Jinja2 template, with values that come from group variables and from facts Ansible gathered about the machine itself. This is how one role serves three shards and a laptop-sized dev box.

roles/clickhouse/templates/cluster.xml.j2
<clickhouse>
  <remote_servers>
    <analytics>
      {% for host in groups['clickhouse'] %}
      <shard>
        <replica>
          <host>{{ hostvars[host].private_ip_address }}</host>
          <port>9000</port>
        </replica>
      </shard>
      {% endfor %}
    </analytics>
  </remote_servers>

  <!-- derived from the machine, not hardcoded: 60% of real RAM -->
  <max_server_memory_usage>
    {{ (ansible_memtotal_mb * 0.6 * 1024 * 1024) | int }}
  </max_server_memory_usage>
</clickhouse>

The handoff from Terraform

Nobody maintains a list of IP addresses. Ansible reads the inventory straight from the AWS API, and the AnsibleGroup tag you saw Terraform set in the last module is what puts each instance into the right group. Add a fourth ClickHouse node in Terraform and it appears in Ansible’s inventory on the next run, with no file to edit.

    separator: ""

site.yml
- name: Analytics nodes
  hosts: clickhouse
  become: true
  serial: 1          # one box at a time; never take the whole cluster down
  roles:
    - role: baseline       # users, ssh hardening, node_exporter, log shipping
    - role: clickhouse
      vars:
        clickhouse_version: "24.8"
        clickhouse_keeper_hosts: "{{ groups['clickhouse'] }}"
Dry runs are free

ansible-playbook --check --diff is Ansible’s answer to terraform plan: it reports what would change and prints a unified diff of every file it would rewrite, without touching the hosts. It is less complete than a Terraform plan — tasks that depend on the result of an earlier task can’t be simulated — but for config file changes it is exactly what you want before a Friday deploy.

Where the line falls

Terraform and Ansible overlap enough to start arguments. The boundary that holds up in practice:

SignalOwner
It has a cloud API, and an ID you could look up in the consoleTerraform
It can be created and destroyed as a unit, and has a bill attachedTerraform
It lives inside a filesystem on a machine that already existsAnsible
It is a package, service, mount, sysctl, user, cron or config fileAnsible

Don’t create cloud resources with Ansible

The amazon.aws collection can make an RDS instance. It has no state file, so it cannot tell “this needs creating” from “this drifted”; it has no plan, so you cannot review the change; and it will not notice when someone deletes something. You would be reimplementing Terraform, badly.

Don’t deploy Kubernetes apps with Ansible

A task that runs kubectl apply works on Tuesday and betrays you in March. It only converges when a human runs it, so a hand-edited Deployment stays hand-edited; there is no record of what is currently live; and your rollback plan is “find the old playbook run”. That is precisely the gap Argo CD exists to fill.

In a fully managed setup, Ansible may have nothing to do

If every data service is managed and every workload is a container on cattle nodes built from a golden AMI, there is no machine for Ansible to configure and no reason to adopt it. Its territory is the long tail: analytics clusters you run yourself, on-prem hardware, network appliances, CI runners, bastions, and the twelve-year-old box nobody will let you delete.

Helm

13 min

Kubernetes wants YAML. Not one file — for the api service alone you need a Deployment, a Service, an Ingress rule, an HPA, a ConfigMap, a ServiceAccount and a PodDisruptionBudget. Then you want all of that again for staging, with different numbers.

The naive approach is a k8s/prod/ directory and a k8s/staging/ directory, copied from each other. It works for about six weeks. Then staging has a readiness probe prod doesn’t, nobody knows whether that was deliberate, and the two directories have quietly become two different applications.

Helm fixes one specific thing: it separates the shape of your application from the numbers in it. Shape goes in templates, written once. Numbers go in values files, one per environment. Helm renders them together into plain Kubernetes YAML.

Three words

  • A chart is a directory: metadata, templates, and default values. It is versioned and can be published to a registry like any other package.
  • Values are the inputs. They layer: the chart’s own values.yaml at the bottom, then each -f file in order, then any --set on the command line. Later wins, and merging is deep, so a prod file only needs to state what differs.
  • A release is one installed instance of a chart, with a name and a namespace. It has a revision history, which is what makes helm rollback possible.

The live renderer below is the part worth spending time on. On the left are the inputs; the middle tab is the template that never changes; the right is what actually gets sent to Kubernetes.

helm template urlshort ./charts/urlshort

Where your compose Postgres went


    
This is the question that makes Helm click. In compose, db and cache were containers in the same file as your app. In production they are RDS and ElastiCache, made by Terraform, and not part of the chart at all. But you still want helm install on a laptop cluster to give you a working stack.

      Endpoints yes, passwords no
      
The Redis and Kafka addresses above are committed to Git, and that is fine — they are unreachable outside the VPC and they are not credentials. The Postgres password is not in that file and never will be. The chart carries only the Secrets Manager ARN that Terraform output, and an ExternalSecret object resolves it into a real Kubernetes Secret inside the cluster at runtime.

    


    
The commands you will actually type


    

      
terminal


# pull the subcharts listed in Chart.yaml into charts/
helm dependency update charts/urlshort

# render locally and read it. do this before every non-trivial change.
helm template urlshort charts/urlshort -f charts/urlshort/values-prod.yaml

# what would change against what is actually running right now?
helm diff upgrade urlshort charts/urlshort -f values-prod.yaml   # plugin, worth installing

# install or upgrade. --atomic rolls back automatically if the rollout fails.
helm upgrade --install urlshort charts/urlshort \
  --namespace urlshort --create-namespace \
  -f charts/urlshort/values-prod.yaml \
  --set image.tag=v1.8.4 \
  --atomic --timeout 5m

helm history urlshort -n urlshort
helm rollback urlshort 7 -n urlshort

    


    

      You will stop typing most of these
      
Once Argo CD is in the picture, nobody runs helm upgrade against production — Argo renders the chart itself and applies the result. helm template stays essential for local review. helm history and helm rollback mostly stop being meaningful, because Argo does not create Helm release secrets; helm list against that namespace will look empty. Your rollback becomes a Git revert instead. This surprises people, so it is worth knowing before the first incident.

    


    
Two failure modes


    

      

        
Over-templating

        
Every field becomes {{ .Values.something }}, the templates turn unreadable, and the values file grows to four hundred lines that nobody can reason about. Template what actually differs between environments. If no environment has ever set it differently, hardcode it — you can always template it later, in one commit.

      

      

        
Copying a public chart into your repo

        
Vendoring bitnami/postgresql so you can tweak two lines means you own its upgrades forever. Prefer values overrides; if you truly need to change the shape, put your own thin chart on top and keep the upstream as a dependency.

      

    


    

      One genuinely great trick
      
The checksum/config annotation in the rendered Deployment above is a hash of the ConfigMap. Kubernetes will not restart pods when a ConfigMap changes — they keep the old values until something else triggers a rollout. Hashing the ConfigMap into the pod template means editing your config changes the pod spec, which triggers a normal rolling update. Nearly every mature chart does this.

Argo CD

      12 min
    

    
You have a chart that renders correct manifests. Something has to get them into the cluster, every time they change, and notice when the cluster stops matching. That is the whole of Argo CD.


    
Why not just run helm upgrade from CI?


    
You can, and plenty of teams do. It breaks down in three predictable places.


    
    
      
  • Credentials point the wrong way. Push-based CD means your CI system holds admin credentials to production Kubernetes. Every build, every fork of a pull request, every compromised action in your workflow is now adjacent to your cluster.
    • 
      
  • It only converges when a pipeline runs. Someone runs kubectl edit deploy/api during an incident and bumps a memory limit. That edit survives until the next deploy silently reverts it — possibly weeks later, possibly at 2am, and nobody connects the two events.
    • 
      
  • Nothing describes the current state. To answer “what is running in prod right now?” you read CI logs and hope the last green build was the last thing applied.
    • 
    


    
Argo CD inverts it. An agent runs inside the cluster, holding no external credentials. It watches a Git repository, compares it against live objects, and reconciles the difference. Git becomes the description of the system, and the cluster becomes a cache of Git.


    
The loop


    
Every few minutes — or instantly on a webhook — the controller renders your chart, diffs the result against what is live, and records two independent statuses. People conflate these constantly:


    
    
      
  • Sync status answers “does the cluster match Git?” — Synced or OutOfSync.
    • 
      
  • Health status answers “are those objects actually happy?” — Healthy, Progressing, Degraded.
    • 
    


    
An app can be perfectly Synced and completely Degraded: you committed a broken image tag, Argo applied it faithfully, and every pod is in CrashLoopBackOff. Argo did its job. Your image is broken.

Turn off self-heal, then scale the deployment by hand. Argo notices within seconds and reports OutOfSync forever, but leaves your change alone — which is exactly what you want during an incident, and exactly what you don’t want the rest of the time. With self-heal on, the same manual scale is undone on the next comparison. Most teams run automated sync with self-heal on, and turn it off deliberately while firefighting.

  


  

    
The Application object


    
Everything above is configured by a single Kubernetes resource. Note what it contains: where the chart is, which values files to layer, where to put the result, and how aggressive to be.


    

      
argocd/applications/urlshort-prod.yaml


apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: urlshort-prod
  namespace: argocd
spec:
  project: urlshort

  source:
    repoURL: https://github.com/acme/urlshort-deploy
    targetRevision: main
    path: charts/urlshort
    helm:
      valueFiles:
        - values.yaml
        - values-prod.yaml

  destination:
    server: https://kubernetes.default.svc
    namespace: urlshort

  syncPolicy:
    automated:
      prune: true      # objects deleted from Git get deleted from the cluster
      selfHeal: true   # manual changes to live objects get reverted
    syncOptions:
      - CreateNamespace=true
      - ApplyOutOfSyncOnly=true
    retry:
      limit: 3
      backoff: { duration: 15s, factor: 2 }

  # tolerate fields that other controllers legitimately own
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers: ["/spec/replicas"]   # only if an HPA manages this

    


    

      prune is the one to think about
      
prune: false means deleting a template from your chart leaves the object running in the cluster forever, accumulating orphans nobody dares remove. prune: true means a bad refactor that accidentally drops a template deletes that object from production. Turn it on, and rely on your chart being reviewed like code — which it now is, because it is a pull request.

    


    
Two repos, not one


    
The conventional split: application source in one repo, deployment config in another. CI builds the image, pushes it, and makes a one-line commit to the deploy repo. Argo sees the commit and rolls it out.


    

      
.github/workflows/release.yml — the last step


- name: Build and push
  run: |
    docker build -t $ECR/urlshort-api:$GITHUB_SHA .
    docker push $ECR/urlshort-api:$GITHUB_SHA

- name: Point staging at the new image
  run: |
    git clone https://github.com/acme/urlshort-deploy deploy
    cd deploy
    yq -i '.image.tag = "'"$GITHUB_SHA"'"' charts/urlshort/values-staging.yaml
    git commit -am "staging: urlshort-api $GITHUB_SHA"
    git push
# Nothing here has kubernetes credentials. The commit is the deploy.

    


    
Promotion to production is then a pull request that copies one line from the staging values file to the production one. It is reviewable, it is revertable, and the diff is the deploy.


    

      Argo CD Image Updater
      
There is a component that watches your registry and bumps tags for you, so CI does not need to commit at all. It is convenient for staging and I would think hard before using it for production: an explicit commit gives you an author, a review, a timestamp and a revert. Automatic promotion gives you a deploy nobody decided to do.

    


    
Ordering: database migrations


    
Your migration must finish before the new pods start, and both must happen in one sync. Sync waves are how you say so — lower numbers go first, and Argo waits for each wave to become healthy before starting the next.


    

      
charts/urlshort/templates/migration-job.yaml


apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "urlshort.fullname" . }}-migrate-{{ .Values.image.tag | replace "." "-" }}
  annotations:
    argocd.argoproj.io/sync-wave: "-1"          # before everything else
    argocd.argoproj.io/hook: Sync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.registry }}/urlshort-api:{{ .Values.image.tag }}"
          command: ["/app/urlshort", "migrate", "up"]

    


    
Closing the secrets loop


    
Back in module 1, Terraform output a Secrets Manager ARN and deliberately did not output the password. Here is where that arrives in the cluster. No credential is ever in Git, and no human copies one.


    

      
charts/urlshort/templates/externalsecret.yaml


apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: {{ include "urlshort.fullname" . }}-pg
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secretsmanager    # authenticates with an IRSA role Terraform made
    kind: ClusterSecretStore
  target:
    name: urlshort-pg           # the k8s Secret the Deployment mounts
  dataFrom:
    - extract:
        key: {{ .Values.postgresql.secretRef }}   # the ARN from terraform output

    


    
Many environments, one definition


    
Writing an Application per environment by hand recreates the copy-paste problem Helm solved. ApplicationSet generates them.


    

      
argocd/appsets/urlshort.yaml


apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: urlshort
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - list:
        elements:
          - env: dev
          - env: staging
          - env: prod
  template:
    metadata:
      name: 'urlshort-{{.env}}'
    spec:
      project: urlshort
      source:
        repoURL: https://github.com/acme/urlshort-deploy
        targetRevision: main
        path: charts/urlshort
        helm:
          valueFiles:
            - values.yaml
            - 'values-{{.env}}.yaml'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'urlshort-{{.env}}'
      syncPolicy:
        automated: { prune: true, selfHeal: true }

    


    
One list, three environments, three Application objects generated and kept in step. If production should not sync automatically — a common and reasonable choice — give it its own hand-written Application rather than bending the generator into knots over a single exception.


    

      Rollback is a revert
      
Argo CD has a rollback button, and it works, but using it puts the cluster deliberately out of sync with Git — the next automated sync will undo your rollback. The correct move during an incident is git revert and push: it fixes production in the same thirty seconds, leaves Git true, and leaves a record of what happened. Reach for the button only when Git itself is unreachable.

resource "helm_release" "argocd" {
  name             = "argocd"
  namespace        = "argocd"
  create_namespace = true
  repository       = "https://argoproj.github.io/argo-helm"
  chart            = "argo-cd"
  version          = "7.6.12"
  values           = [file("${path.module}/argocd-values.yaml")]
}

# the single seed. everything else arrives through git from here.
resource "kubectl_manifest" "root_app" {
  yaml_body  = file("${path.module}/root-application.yaml")
  depends_on = [helm_release.argocd]
}

The handoffs


    
Each tool publishes something the next one consumes. None of them import each other’s internals, and no human copies a value between two files.


    

      
From → toWhat travels

      
        
Terraform → AnsibleEC2 instance tags. Ansible’s dynamic inventory queries the AWS API and groups hosts by AnsibleGroup.

        
Terraform → HelmOutputs. Non-secret endpoints are committed into the environment’s values file; secret material travels only as an ARN.

        
Terraform → Argo CDOne bootstrap: Argo CD installed, and a root Application pointing at the deploy repo.

        
Helm → Argo CDThe chart path and the list of value files, named in the Application spec. Argo runs the rendering itself.

        
CI → Argo CDA one-line commit changing image.tag. No cluster credentials involved.

The five mistakes worth naming


    

      

        
Local Terraform state

        
Fix it on day one. The second engineer to join is the incident.

      

      

        
Deploying the app from Terraform

        
helm_release for the thing you ship weekly puts app releases in infrastructure state and gives your deploy pipeline admin on the cloud account.

      

      

        
Ansible running kubectl apply

        
All of the ceremony of GitOps with none of the convergence. If the target is Kubernetes, the answer is Argo CD.

      

      

        
helm upgrade from a laptop

        
The change is real, the Git history is fiction, and the next sync silently erases it. Whatever is true must be committed.

      

      

        
Secrets in values files

        
Private repositories are not a secrets management strategy. ARNs in Git, values in the cluster, resolved at runtime.

      

      

        
And one thing to keep doing

        
Read the plan. terraform plan, ansible-playbook --check --diff, helm template, the Argo diff view. All four tools will show you exactly what they are about to do, and the discipline transfers between them.

Where to go from here

    
The fastest way to make this stick is to build a smaller version of it. A single-node k3s or kind cluster on your laptop, a chart for one service, Argo CD installed and pointed at a GitHub repo you own. You can have the whole loop working in an evening, and the moment you watch Argo undo a kubectl edit you will never need to reread module 4.

    
Terraform is harder to practise cheaply, but it does not need a cloud bill: point it at your own GitHub organisation or a Cloudflare zone and manage those as code. The state, plan and graph lessons are identical, and the mistakes cost nothing.
