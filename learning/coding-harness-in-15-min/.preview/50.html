the core code

The pruning step is one filter

src/pruner.ts

export function pruneMessages(messages, indexer) {
return messages.filter((msg) =>
!(msg.role === "toolResult" &&
indexer.isSummarized(msg.toolCallId)));
}

One function, a handful of pi.on calls, two tools, a command. [1] The one that matters: context. [2] The whole pruning algorithm is one filter: drop toolResults whose ID is in the index. [3] Early exits return undefined: disabled, or nothing to drop. Untouched messages keep the prompt cache stable. [4] Otherwise return new messages, for this request only. The model sees a summary; the session keeps everything; no fork of pi. That's the lesson. One breath, only if time: five flush modes trade cache hits against context size (default once per task, every-turn is leanest but busts the cache most, plus on-demand /pruner now and model-driven ones). If a summary would be bigger than the raw output the batch is skipped, and if the summarizer fails the batches go back to pending.
