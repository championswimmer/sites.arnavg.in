…so the loop ends. One prompt, four model calls.

This is the core of every coding agent. The task: "fix the failing login test". The file names, test output and the fix itself are illustrative, and the size bar has no real numbers. The loop structure is pi's real code path. Step 1 (Input): you type one line. pi first checks for built-in and extension slash commands, expands skills and prompt templates, then builds the user message. Step 2 (Context): the harness assembles what the model sees. The system prompt comes from buildSystemPrompt: tool snippets, guidelines, AGENTS.md context files, skills, the cwd. Then the tool definitions and the message history. The model knows only what is in this stack. Step 3 (Provider): pi-ai turns that provider-neutral context into an HTTP request for Anthropic, OpenAI, Google, Bedrock or others. Note the label on the right: the whole stack is sent on every call, not just the new message. Step 4 (Stream): the answer streams back as normalised events: text deltas, thinking deltas, tool-call deltas. Here it says it will run the tests and emits a tool call for bash. Step 5 (Tool calls): the harness looks up the tool, validates the arguments against its schema, and runs it. pi runs multiple tool calls in parallel by default. Step 6 (Tool results): the output is wrapped as a toolResult message and appended. Because there were tool calls, the loop goes back to Context and calls the model again. Steps 7–8: two more laps: read the file, then edit it. Watch the context stack: the test log and the whole file are still in there, and they are re-sent on every later call. Hold that thought; the context-prune extension later in the talk deals with exactly this. Step 9–10: the model replies with plain text and no tool calls, so the inner loop exits and the run is done. Between laps pi can also auto-compact if the context gets too big, and after the run it may retry an error. One prompt from you, four model calls, three tool runs, all driven by the harness. Demo tip: the "auto-play loop" button steps through the whole loop on a timer; click it again to pause.

Everyone compares models. Very few people compare harnesses, but the harness sets most of these dials. Both columns here send requests to the same model. Dial 1, context: by default pi keeps every tool output in context until compaction summarises the older part. With the context-prune extension, outputs from a finished task are swapped for short summaries in the model's view, while the originals stay in the session. Dial 2, tools: pi's defaults are read, bash, edit and write. An extension can register new tools, like the checklist extension's three tools, or block a call such as rm -rf before it runs. Dial 3, stopping: by default the loop ends when the model replies without tool calls. A tool can also return terminate to end the run. Dial 4, what you see: the TUI shows the transcript, editor and footer. Extensions can paint the footer and widgets: speedometer shows tokens per second, and checklist shows task progress. Dial 5, what's saved: pi writes a JSONL session file shaped like a tree, and extensions can store their own state entries in that same file. Step 6: nothing about the model changed. Every difference in the right column is harness code, and each one is a real extension you'll see later in this talk.

Part two. We've just seen the loop every coding harness runs: input, context, the model call, streaming, tool calls, tool results, and around again. Pi's key idea is that every one of those stages fires a named, typed event. An extension is just code that subscribes to those events. Some events only tell you what happened. Others let you return a value that changes what happens next. Those are the ones marked with a pencil throughout this section. By the end of this section you should recognise names like context, tool_call, message_update and before_agent_start when they show up in the three real extensions.

Pi's agent loop. Each stage fires named, typed events.

Input: the prompt arrives. The run hasn't started yet.

Context: a turn starts; you can rewrite what the model sees.

Provider: headers, the raw request payload, the response.

Stream: one message_update per delta.

Tool calls: inspect, patch or block before execution.

Tool results: patch the output before the model reads it.

Tools ran, so the loop goes round again.

Turn 1: the model sees the results and answers in text.

No tool calls: turn_end → agent_end → agent_settled.

Every ✎ chip: return a value and pi does something different.

This is the same loop as the previous section, now with pi's real event names attached to each stage. Click through, and chips glow as they fire. Click any chip at any time to open its inspector: when it fires, its payload, and what it can return. Step 1, Input: session_start fired once when pi started. Each prompt then fires input (you can transform the text or swallow it entirely), before_agent_start (inject a message or change the system prompt for this run), then agent_start. Step 2, Context: turn_start, then context, which gets a deep copy of the messages right before every LLM call. Gotcha: on turn 0, turn_start actually fires BEFORE the user message's message_start and message_end. The official docs diagram draws it the other way round, but the source is clear. Step 3, Provider: before_provider_headers (mutate headers in place), before_provider_request (see or replace the exact provider payload), after_provider_response (status and headers). Step 4, Stream: message_start when the stream starts, a message_update for every thinking, text or tool-call delta, and message_end when it's final. message_end can replace the message before it's written to the session file. Step 5, Tool calls: tool_execution_start, then tool_call after argument validation and before execute. This is where you block things. tool_execution_update streams partial output. Tools run in parallel by default. Step 6, Tool results: tool_result can patch content, details or isError, chained like middleware. Then tool_execution_end, and each toolResult message gets its own message_start and message_end. Step 7: turn_end with the assistant message and all its tool results. There were tool calls, so we go round again. Step 8: turn 1 goes through context, provider and stream again, now including the tool results. This time the model just answers. Step 9: no tool calls, so the inner loop exits: turn_end, agent_end, and agent_settled once there's nothing left to retry or compact. Step 10: the amber chips are the ones where a return value changes behaviour. 14 of the 36 events work that way; eight of them are on this loop. Important: handlers run before the TUI renders the event, and before the message is persisted.

Step 0: An extension is a TypeScript file whose default export is a function. Pi calls that function once at load time and hands it the ExtensionAPI object, which we call pi. Step 1: The factory is where you wire everything up. Drop the file into ~/.pi/agent/extensions for global use, or .pi/extensions in a project (project-local ones load only once you trust the project). Type /reload and it's live. This is the whole extension running in slow motion. All numbers are illustrative but internally consistent, from the research walkthrough: first delta at 840ms, a delta every 20ms, 168 deltas, message_end at 4.2 seconds with 310 output tokens. Step 1, t = 0: pi fires before_provider_request right before the HTTP call. That hook is meant for inspecting or rewriting the payload; we just use it as a starting gun. performance.now(), reset a few variables, return nothing. Step 2, the wait: message_update events of type start and text_start can arrive, but they carry no content, so the handler ignores them. This dead air is network, queueing and prefill of your whole context. Step 3, 840ms: first text_delta. Freeze TTFT at 840ms. There's no TPS yet because zero seconds have passed since the first token, and the code guards against divide-by-zero, so for one frame the footer shows only the stopwatch. Step 4, 2.14s: deltas arrive about 50 times a second. Repainting the footer that often is waste, so it throttles to 250ms; with deltas on a 20ms grid that is a render every 260ms. Point at the maths: 122 tokens divided by 1.30 seconds since the first token is 93.8. 168 deltas produce only 13 status writes. Step 5, 4.2s: message_end carries the real usage: 310 tokens over 3.36 seconds is 92.3 tokens per second. That final value stays in the status bar after the turn. In an agent loop, the next LLM call fires before_provider_request again and re-anchors the clock. Demo: click "replay in real time" to run the full 4.2 seconds at real speed; 0.25× slows it down so people can watch the footer tick. Caveat, say this only if asked: live TPS depends on the provider reporting partial usage. Google sends usage on every chunk; OpenAI chat completions only in the final chunk, so the extension estimates chars ÷ 4 until message_end snaps to exact. The README says Anthropic streams cumulative output counts, but pi's Anthropic adapter appears to set usage.output only at message_start (usually 1) and at the final message_delta, so the mid-stream number could read very low, like 3.8 t/s, until message_end fixes it. Test with a live Claude run before claiming exact live TPS on Anthropic. The final number is correct either way.

This is every hook the extension registers. Bodies are elided; the skeleton is lines 116 to 194 of the single source file. Step 1: before_provider_request starts the clock. requestStart = performance.now(), and it resets firstDeltaTime, the throttle timestamp, the token count and TTFT. It ignores the payload and returns undefined, so the request goes out unchanged. Step 2: message_update. It returns early unless the stream event is a text, thinking or tool-call delta. On the first one it records firstDeltaTime and computes TTFT. On every one it updates the token count, and only if 250ms have passed does it call renderStatus, which does tokens divided by seconds since the first delta and calls ctx.ui.setStatus with the key "speedometer". Step 3: message_end. It fires for user and tool-result messages too, so it checks role is assistant. It snaps the token count to message.usage.output, which is the exact number, and does one final unthrottled render. Step 4: agent_end and session_shutdown just set streaming to false and leave the final numbers in the footer. /speed toggles each metric on or off and switches icon or text labels, saved to ~/.pi/agent/pi-speedometer.json. Stats: 233 lines total, one file, no runtime dependencies and no build step, because pi loads the .ts directly. Of that, settings load/save is about 45 lines and /speed about 40; the actual measurement logic is about 55. Optional aside, "even tiny extensions have edge cases": after /speed toggles, the re-render passes performance.now() as the end time rather than when the stream ended. So toggling a label 60 seconds after a response recomputes TPS over 63 seconds and shows something like 4.9 t/s. The fix is storing the end time at message_end: a one-line PR.

Step 0: The user types "add rate limiting to the API" and presses Enter. No checklist exists yet. Step 1: before_agent_start fires once per user prompt, before the agent loop. There's no list, so it only appends the moderate usage hint. The promptGuidelines bullets from the three tools are already in the Guidelines section. It's plain text and costs very little. Step 2: The model calls checklist_create. It passes explicit 3-char ids because the dependencies point at tasks created in the same call, which is exactly what the tool guideline recommends. Without explicit ids it would get hashed ids like q6z. The content text goes to the model. The details field holds the full snapshot: it's saved on the tool result and drives the renderer, but it isn't sent to the model. commit() appends a pi-checklist entry, the widget repaints, and the footer shows ☑ 0/4. stg is ready; the rest are blocked. Step 3: The guideline says mark a task ongoing before starting it, so the human always knows what the agent is doing now. The call renders as "checklist stg". On the next user prompt, the injected snippet lists the open tasks, so even after compaction the model still sees the plan. Step 4: Here the model jumps ahead and tries to mark stg done and wir done in one batch. wir depends on mid, and mid isn't done, so the store throws. pi turns the thrown error into isError: true, and the model reads the exact message on screen. Because updates are all-or-nothing, even the valid stg → done is discarded. commit() never runs, so no entry is appended and the widget doesn't change. The extension enforces order; it doesn't just record it. Step 5: The error named the blocker, [mid]. The model finishes stg and starts mid in one call. Order within a batch matters: stg done first, then mid ongoing succeeds. The reverse order would fail. Footer: ☑ 1/4. Step 6: Fast-forward through three more updates to ☑ 4/4. On the next user prompt nothing is planned or ongoing, so before_agent_start appends only the hint and no task snippet. Three excerpts, one at a time. The tabs are clickable if you want to jump. Step 0, registerTool: everything the model sees comes from this object. The description, a one-line promptSnippet in the "Available tools" list, promptGuidelines bullets appended to the Guidelines section (pi's docs say each bullet must name the tool, never "this tool"), and a TypeBox schema for the parameters. There are three of these registrations: create, read and update. Step 1, execute: run a pure store function, commit the new snapshot, and return two things. content is the text the LLM reads. details is structured data that isn't sent to the LLM but is saved on the tool-result entry. Validation errors are thrown from the store before commit runs, so pi reports them to the model as isError and nothing is persisted. Step 2, renderers: renderCall and renderResult are the human-facing half of the same registration. Instead of a raw JSON dump you see "checklist create 4 task(s)" and "0/4 done 0 ongoing 1 ready 3 blocked", read from result.details. Step 3, before_agent_start: it fires once per user prompt. It returns a new systemPrompt: the original, plus the hint, plus the open-task snippet if anything is planned or ongoing. System-prompt changes chain across extensions. The usage mode is captured at load, so changing it needs /reload. Step 4, appendEntry: commit does three things: update the in-memory cache, append a "pi-checklist" custom entry, and repaint. The try/catch matters because print or ephemeral sessions have no file. The custom entry covers human actions like /checklist clear that never produce a tool result. Size check: index.ts, the pi wiring, is 324 lines. store.ts and types.ts, about 640 lines, are plain TypeScript with no pi imports, testable with plain node.

03 / pi-context-prune

pi-context-prune

Rewrite what the model sees on every request.
Keep the truth on disk.

Now the first real extension. You know the loop and you know the hooks. This one uses them to do something you can't do from a prompt: it rewrites what the model sees on every request, without touching the saved session, and it gives the model a tool to get things back. This is the whole extension mapped onto the lifecycle you just saw. The ✎ marks the hooks whose return value changes what pi does. [1] session_start and session_tree: on startup, reload or /tree navigation it reloads config and rebuilds its index from the current branch, so state is branch-aware. [2] before_agent_start: only in agentic-auto mode, it appends instructions to the system prompt telling the model when to call context_prune. [3] context: the important one. It runs before every LLM call and filters out tool results that are already summarized. It changes that one request only. [4] turn_end: after each turn with tool calls it captures a batch: the assistant text plus each call and its result. Nothing is summarized yet. [5] message_end: in the default agent-message mode, the first assistant message with no tool calls means the task is done, so it flushes. [6] A registered tool, context_tree_query, which is the recovery path. [7] A /pruner command with subcommands. Also, tool_execution_end triggers on-context-tag mode, agent_end only updates status, and a second tool, context_prune, exists for agentic-auto.

Token counts are illustrative estimates (about 4 chars per token). The events, field names and ordering are exact. Settings: /pruner on, default prune-on agent-message. [0] Request 1. The context hook runs before every LLM call. The index is empty, so it returns undefined and pi sends the messages unchanged. [1] The model calls read and bash in one assistant message, and pi runs them in parallel. 12,000 and 24,000 chars land in context. [2] turn_end fires with the assistant message and its tool results. captureBatch builds this object: turnIndex, assistantText, and each toolCallId, toolName, args, resultText, isError. It goes into pendingBatches. Nothing is summarized yet. [3] Why wait? The prompt cache. Every time you rewrite earlier messages, the cached prefix from that point is invalidated. So the default batches a whole task. Turn 1: grep, 2,000 tokens, second batch queued. (context also ran for requests 2 and 3 and returned undefined.) [4] The model answers in plain text. In agent-message mode, message_end with an assistant message that has zero toolCall blocks means the task is done, so flushPending runs, with session delivery. [5] The flush re-scans the session branch, then summarizeBatches makes one LLM call per batch, in parallel with Promise.all. It's the active model by default, or a cheap one you configure. Each tool result is cut to its first 2,000 chars, so the summarizer sees about 1,000 tokens of the 9,000. [6] Each summary gets short refs: turn 0 gets t1 and t2, turn 1 gets t3. There's a size check: if the summary is bigger than the raw output, the batch is skipped. [7] Two kinds of session entries: a custom_message with the summary, which is sent to the model as user-role text but hidden in the transcript, and a custom index entry with the full originals, which pi never sends. Plus a frontier and a stats snapshot. Note the context is still exactly as big. [8] You say "OK, fix it". Request 4 is being built. context gets a deep copy of the messages. Unpruned, this would be 13,875 tokens. [9] The filter drops every toolResult whose ID is indexed. Assistant tool-call blocks stay, so the IDs are anchors; pi's provider layer inserts tiny "No result provided" placeholders for the orphaned calls. 13,875 becomes about 3,160, which is 77% smaller. CAVEAT (say it carefully): this frame shows the intended design, with the summaries in context. In the session delivery modes (agent-message, every-turn) the summary is written with sessionManager.appendCustomMessageEntry, which may not reach the live agent's in-memory messages until a reload or tree navigation. The raw results are still removed immediately, and recovery still works. Runtime delivery (/pruner now, on-context-tag, agentic-auto) uses pi.sendMessage with deliverAs "steer", which doesn't have that gap. For the live demo use: /pruner on, /pruner prune-on on-demand, /pruner now, then /pruner tree and /pruner stats. [10] The session file was never rewritten. Every raw tool result is still on disk; the extension only added entries. Pruning is a view, not a delete.

Hot context, cold storage, one tool between them

Illustrative token counts again. [0] After pruning we're at about 3,160 tokens. The summary says one test failed. But the summarizer only saw the first 2,000 characters of the jest log, and the failure detail is near the end. [1] So the model calls context_tree_query with the short ref t2, which it read in the summary footer. The tool is always registered, and its promptSnippet and guidelines tell the model when to use it. It takes short refs or full tool call IDs; an unknown ref comes back as "not found in index". [2] The indexer resolves t2 to toolu_01NpmTest and returns the full stored output as a new tool result: tool, args, status, turn, then the log, capped with truncateHead at 2,000 lines or 50 KB. Now the model sees "Expected 401, received 200, at login.test.ts line 57". Context goes back up to roughly 9,200. [3] That recovered output is a new tool result, so at the next flush it gets summarized and pruned again with a new ref. Think hot memory versus cold storage.

the core code

The pruning step is one filter

src/pruner.ts

export function pruneMessages(messages, indexer) {
return messages.filter((msg) =>
!(msg.role === "toolResult" &&
indexer.isSummarized(msg.toolCallId)));
}
