How a bare-metal cloud gives you a hard drive that never dies and grows on demand

Ceph + ZFS is the combo behind "attach a volume to your app, grow it whenever, and never lose the data." Here's the whole stack, explained for someone who has never touched either.

CephRADOS · RBDZFS · zpool · zvolContainersBare metal

Imagine you run a hosting platform on your own hardware — racks of servers in a datacenter, no AWS underneath. A customer deploys a database and clicks "add a 20 GB volume." You now owe them storage that:

  • survives failure — a disk dies, or a whole server catches fire, and their data is still there;
  • follows the app — if their container moves to a different machine, the data moves with it;
  • grows on demand — 20 GB today, 200 GB next month, no downtime;
  • doesn't waste money — you don't buy 20 GB of physical disk for a volume that's 2 GB full.

A single hard drive plugged into a single server can't do any of that. So you build the storage in two layers that each solve half the problem: Ceph for durability and mobility, and ZFS for efficiency and per-customer features. Let's build it from the bottom up.

01What Ceph is

Start with the problem Ceph solves. You have hundreds of hard drives scattered across dozens of servers. Left alone, each is an island: a 4 TB drive in server 7 is just 4 TB of storage that dies when server 7 dies. Ceph glues all of them into one giant shared pool that behaves like a single, enormous, self-healing storage system.

ELI5

Think of one massive warehouse built out of thousands of tiny storage lockers spread across several buildings. You don't care which locker your box is in — you hand it to the system and it stashes three copies in three different buildings. If a locker breaks, or a whole building loses power, your box is still safe in the other two, and the system quietly makes a fresh third copy somewhere else. That self-healing warehouse is Ceph.

The clever part is that there's no central librarian that every request has to go through (that would be a bottleneck and a single point of failure). Instead, a shared math formula lets any client calculate exactly which drives hold a given piece of data. That's how Ceph scales to thousands of disks without choking. Here are the pieces you'll hear named:

PieceELI5 job
OSD
Object Storage Daemon		One worker per physical disk. It actually reads and writes the bytes. 100 disks ≈ 100 OSDs.
Monitor (MON)The small council (usually 3 or 5) that holds the official map of the cluster — who's alive, where things live. They vote so they always agree.
Manager (MGR)The bookkeeper — metrics, dashboard, health. Keeps the humans informed.
RADOSThe engine underneath it all. Everything in Ceph is ultimately objects spread across OSDs; RADOS is what stores and replicates them.
CRUSHThe map + formula that decides which OSDs hold which data — deterministically, so no lookups needed.
PoolA logical slice of the cluster with a rule attached, e.g. "keep 3 copies of everything in here."

To stand up a small cluster you'd install these daemons across your servers: a few monitors for quorum, one OSD per disk, a manager or two. Modern Ceph uses a tool called cephadm that deploys them in containers, so bootstrapping looks roughly like: bootstrap the first monitor, add the other hosts, then tell Ceph "turn every spare disk into an OSD." At that point you have a working pool of storage.

02Turning Ceph into a "hard drive": block storage with RBD

A pool of replicated objects is great, but your customer's database doesn't speak "objects" — it wants a plain disk it can format and write files to. Ceph's answer is RBD: the RADOS Block Device.

ELI5

RBD is Ceph wearing a disk costume. You ask for a "50 GB disk" and Ceph hands you something that looks exactly like a normal drive — it shows up on a server as /dev/rbd0, and you can format and mount it like any hard drive. Behind the costume, that "disk" is really chopped into thousands of little objects sprinkled across the whole cluster, each with three copies.

Two things make RBD special compared to a real drive:

  • It's not chained to one machine. The virtual disk lives in the cluster, so any host can attach it. The server it's plugged into is just a temporary renter.
  • It's already backed up. The 3-copies-on-different-hosts rule from the pool applies automatically. Lose a disk or a whole server and the RBD keeps working without a blip.
# carve a 50 GB virtual disk out of the pool, then attach it to this host
rbd create volumes/vol-a --size 50G
rbd map volumes/vol-a        # → now visible as /dev/rbd0

So after this step you have, on some host, a device at /dev/rbd0 that acts like a disk, survives hardware death, and can be re-attached elsewhere. That's the durable, movable foundation. Now we make it smart.

03ZFS on top: efficiency, snapshots, and growing on demand

Ceph gave us a disk that won't die. But we still want the money-saving and feature tricks: don't reserve space you're not using, compress data automatically, take instant backups, and resize without downtime. That's ZFS — a filesystem and volume manager fused into one very clever piece of software.

ELI5

If Ceph is the warehouse, ZFS is the brilliant organizer you put in charge of one room. You give ZFS a disk — here, our Ceph RBD — and it turns it into a zpool. Out of that pool the organizer can hand out any number of labelled compartments (datasets), each acting like its own drive, while quietly compressing everything, only using the shelf space actually filled, and being able to photograph the whole room in an instant so you can rewind to how it looked yesterday.

You point ZFS at the Ceph block device and create a pool, then a dataset per customer volume:

# make a ZFS pool that lives ON the Ceph virtual disk
zpool create tank /dev/rbd0

# one dataset per user volume, with the good stuff switched on
zfs create -o compression=lz4 -o quota=20G tank/vol-a
# tank/vol-a is now a folder that behaves like a 20 GB drive

Here's why each ZFS feature earns its place in a hosting platform:

ZFS featureWhat it buys you
Thin provisioningA "20 GB volume" only uses the space actually written. You can promise big volumes without buying the disk up front.
Compression (lz4)Transparently squishes data — often more usable space and faster, because less is read from disk.
SnapshotsInstant, near-free point-in-time copies (copy-on-write). Backups and one-click rollback for the customer.
ChecksumsEvery block is verified on read; silent corruption is caught and repaired from a good copy.
Online resizeGrow the pool and raise quotas live — the basis of autoscaling volumes.

What "autoscalable" actually means here

The magic of stacking these two layers is that every layer is elastic, so a volume can grow while the app keeps running. When a customer's 20 GB volume starts filling up, the platform can, live and in order:

  1. Grow the Ceph disk. rbd resize volumes/vol-a --size 40G — the virtual disk is now bigger, drawn from the cluster's free space.
  2. Grow the ZFS pool into the new space. ZFS notices the underlying device grew and expands to fill it.
  3. Raise the quota. zfs set quota=40G tank/vol-a — the customer's limit is lifted with zero downtime.

And if the whole cluster is running low, you rack another server, add its disks as new OSDs, and Ceph rebalances into the extra capacity automatically. The warehouse itself grows without anyone reconfiguring the customers.

04Mounting it into the container

The customer's service runs inside a container — really just their process with its own private view of the filesystem. To give it persistent storage, you bind-mount the ZFS dataset from the host into the container.

ELI5

A bind-mount is like installing a magic door in the container's wall. Open the door labelled /data inside the container and you step straight into the ZFS compartment on the host. The app just sees a normal folder at /data and writes to it — never knowing that behind the folder is ZFS, behind ZFS is a Ceph virtual disk, and behind that are three copies scattered across the datacenter.

# host path  →  container path
docker run -v /tank/vol-a:/data  my-database

The app writes to /data. Those writes flow down through ZFS (compressed, checksummed), onto the RBD, and into RADOS, which replicates them three times across the cluster. That's the entire round trip.

05Why this combo — and what happens when a server dies

The two layers are a deliberate division of labour:

LayerOwns
CephDurability & mobility — survive dead disks and dead servers; move a volume between hosts.
ZFSEfficiency & features — thin provisioning, compression, snapshots, easy resize.

The payoff is clearest in a failure. Suppose the server running a customer's database suddenly dies:

  1. The data is never lost — Ceph still holds its copies on OSDs on other servers.
  2. The platform reschedules the container onto a healthy host.
  3. That host re-attaches the same RBD (rbd map) — the virtual disk simply moves.
  4. ZFS imports the pool (zpool import tank) and the dataset is back, byte-for-byte.
  5. The dataset is bind-mounted into the new container at /data, and the service is running again.

From the customer's view, their app blinked and came back with all its data. The storage followed the service across the datacenter on its own.

The honest trade-off

Stacking ZFS on top of Ceph RBD means two smart layers that both do copy-on-write and checksumming, which adds some overhead and tuning work — you're paying a little performance for a lot of features. It also means one host "owns" a given ZFS pool at a time (it isn't shared by many machines at once), which fits perfectly with "one volume attached to one service." Teams choose this pattern on purpose: Ceph's durability plus ZFS's per-tenant tricks give you a cloud-grade volume service on hardware you own.

06The whole thing in one breath

Bottom to top: physical disks across many servers → one OSD per disk → RADOS pools them all and keeps three copies → RBD carves out a virtual disk that any host can attach and that can't be killed by hardware failure → ZFS turns that disk into thin, compressed, snapshottable, resizable datasets → each dataset is bind-mounted into a customer's container as /data. Ceph makes the storage indestructible and portable; ZFS makes it cheap, flexible, and feature-rich; the container just sees an ordinary folder that happens to be backed by a whole datacenter.
