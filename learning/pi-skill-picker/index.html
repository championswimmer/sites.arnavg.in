03

Follow one request
through the middle.

“Add a coupon code to checkout and explain the rounding policy.” Here’s how that task becomes a focused skill loadout.

01 / Start with Pi’s inventory

No second scanner.
No invented candidates.

Pi discovers skills from its configured locations. On before_agent_start, the extension takes exactly the skills Pi has already loaded for this session and project.

The picker does not install skills, scan new directories, or load their instruction files.

// src/extension.ts
pi.on("before_agent_start", async (event, ctx) => {
  const skills = event.systemPromptOptions.skills;
  const task = event.prompt;
  // Inventory is supplied by Pi.
});
02 / Establish the boundary

Eligible, enough,
and not already visible.

Deduplicate skill names and exclude disableModelInvocation skills. By default, activate only with at least 30 eligible skills. Disabled or below the gate? Leave Pi’s normal catalog untouched.

For an active turn, restore branch selections and valid project pins. Hide the full catalog before ranking; only pending skills need a score.

// Conceptual policy
eligible = dedupeNames(piLoaded)
  .exclude(disableModelInvocation);

if (!enabled || eligible.length < minSkills)
  keep Pi's normal behavior;
else
  pending = eligible - selected - pinned;
03 / Ask a narrow question

“How useful is this
skill for this task?”

Send bounded task text, an already-available summary, and one five-level Score question per pending skill. The classifier returns rubric ratings—not a plan, generated instructions, or a new skill.

Default batches contain 50 candidates, with at most six concurrent requests. A 300-pending-skill catalog means six batches, not 300 separate calls.

// Simplified Decisions payload
state: { task, already_available }
questions: {
  s0: {
    type: "score",
    instructions: "How useful would this skill
      be for the current task? Name: …
      Description: …",
    criteria: [ five usefulness levels ]
  }
}
04 / Make ratings actionable

Normalize.
Cut off. Rank. Cap.

Validate each Score answer, divide its raw rating by four, and keep scores at or above the threshold. Sort all batch results together, then add at most maxNew skills.

The default cutoff is 0.625; the default addition cap is six per pass. Confidence is not multiplied into usefulness. Missing or malformed answers are ignored.

// Five criteria → top level is 4
normalized = rawScore / 4;

allBatchResults
  .filter(score => score >= 0.625)
  .sort(highestScoreFirst)
  .slice(0, 6);

// These are ratings, not probabilities.

05

Selection isn’t a one-shot bet.

A task can change shape once the agent reads code or runs tests. New completed tool text gives the picker another chance to surface expertise.

Turn starts / before_agent_start

Classify the user’s request.

Restore existing selections and pins; rank the pending catalog against the new prompt. The initial model request sees only the selected set.

First request / context_with_system

Snapshot, don’t classify twice.

The first context hook records the bounded transcript and known tool results, then continues without another ranking pass.

Tools finish / new textual toolResult

The code reveals a database constraint.

A completed read or test result adds new evidence. Streaming tokens and in-progress tool updates don’t trigger decisions.

Next request / context_with_system

Rank only what’s still hidden.

Before the next model call, classify pending skills against bounded recent text. Add new matches and patch only the skills section.

Same session branch

Useful expertise sticks around.

Selected skills remain available across subsequent requests and turns. An unchanged retry doesn’t spend another ranking pass.

Three trigger policies

prompt-only

Pick at turn start. No incremental ranking.

prompt-and-tools

Default. Later passes require a new completed textual tool result.

every-request

Rank on changed extracted transcript text—not literally every retry.

Only active turns with pending candidates can rerank. Image-only tool output does not count as textual evidence.

History follows the branch.

Restore from getBranch(), not the entire session tree. Rematch names to the current Pi inventory; drop stale entries. A new session starts fresh.

↳
Sticky does not mean endlessly tiny. More skills can accumulate over a long branch. The extension caps new additions per pass; it does not evict skills by relevance or enforce a global context budget.

The descriptions don’t disappear from all computation. Pending descriptions go to the classifier; the main model receives only the selection. The benefit is moving routing out of the main model’s context, not making routing free.

This is not a dollar or latency benchmark. Classifier calls add cost and time. Main-model pricing, prompt caching, repeated passes, and growing selections determine the real economics. Priced decision batches are recorded in usage logs.

07

One boundary.
Three classifier backends.

The same selection pipeline can use hosted Jev, a trusted compatible endpoint, or Pi’s classifier registry. The main coding model stays independent.

01 / default

Hosted OpenRouter / Jev

Calls OpenRouter’s Decisions endpoint. Uses Pi’s OpenRouter provider credentials and defaults to typesafe/jev-1.13.

openrouter-jev

Bounded task text and candidate descriptions leave your machine for the hosted service.

02 / your endpoint

Custom HTTP

A TypeSafe-compatible server at /v1/systemone. Defaults to jev-latest; uses only its own configured token, or no authentication.

custom-http

Can point to a local or trusted server. Never inherits Pi’s OpenRouter credentials; redirects are rejected.

03 / Pi’s model registry

Pi classifier

Finds a registered classifier model and calls modelRegistry.classify. Defaults to typesafe/jev-latest.

pi-classifier

Privacy depends on the registered provider. This mode is not automatically local or offline.

Model precedence: saved model setting → PI_SKILL_PICKER_MODEL → backend default. Bounded does not mean redacted: tool text may contain sensitive material. Choose a backend you trust.

08

Selective by default.
Still under your control.

The goal is a quieter context—not a fragile agent that loses access to its skills.

✓

Fail closed on active turns

A missing key or failed ranking does not reveal the full catalog. Existing selections and valid allowlist pins remain; no successful new selection means no new skills. If a batch throws, that ranking pass adds nothing.

↪

Small catalogs can bypass the picker

Below minSkills: 30 or when switched off, leave Pi’s original skills list intact. This is an intentional skip, not fail-open recovery. Set the minimum to zero to disable the size gate.

⌖

Pin the project’s essentials

The project allowlist keeps skills visible without needing task scores. Only currently loaded, model-invocable skills can be injected. A pin is not a way to resurrect stale or disabled entries. The pin editor can also score global importance and topic searches, separately from task ranking.

/

Manual invocation still works

Use /skill:name when you know the exact skill you need. That remains Pi’s native behavior. The picker filters automatic discovery; it does not remove skill files or commands.
