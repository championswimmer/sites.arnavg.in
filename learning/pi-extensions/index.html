01 / The machine underneath

The model emits a tool call; Pi executes it. 02 / Event-driven extension

A hook is a named moment in that loop

Pi emits

event: "tool_call"
toolName: "bash"
input: { command: "npm test" }

An event carries the details available at that moment.

Extension listens

export default function (pi) {
  pi.on("tool_call", (event, ctx) => {
    // inspect, block, or react
  });
}

The default export receives Pi’s extension API. Add one handler; the harness calls it at the boundary.

Hooks can observe events, alter some payloads, or block some actions. The event’s contract decides which.

A Pi extension exports a default function that receives an ExtensionAPI object. Calling pi.on registers a handler. This example uses tool_call, which can inspect a proposed tool and return block=true with a reason. Other hooks have different allowed return values, so never generalize that every hook can modify everything. The snippet is intentionally tiny for a projected slide.

02 / Four ways to extend

Extensions can do more than listen

pi.on(...)

Event handlers

Observe or shape moments in the lifecycle.

Example: trim future context.

pi.registerTool(...)

Agent tools

Give the model a new callable capability.

Example: update a checklist.

pi.registerCommand(...)

User commands

Offer a slash command to control the feature.

Example: /speed or /pruner.

ctx.ui + pi.appendEntry

UI + state

Show status, widgets, dialogs, and session data.

Example: persistent task view.

Extensions may combine these APIs. pi-context-prune uses event hooks and tools. pi-speedometer uses event hooks, a status UI, and a user command. pi-checklist uses tools, commands, UI, and session persistence. Agent tools are callable by the model; slash commands are initiated by the human.

Walk the three handlers left to right. before_provider_request records performance.now() and resets per-request state. message_update ignores non-content deltas, records TTFT only on the first content delta, counts output tokens from partial usage or a rough content-length estimate, and calculates TPS over time since that first delta. Status writes are throttled to once per 250 ms. message_end prefers exact final output usage when available, then leaves the final metrics in ctx.ui.setStatus. /speed only changes display preferences. This extension registers no agent tool and never alters a model request. The shown code is pseudocode compressed for projection; the real source has guards and formatting.

Case study C / pi-context-prune

Tool results can swamp the context

NEXT MODEL REQUEST

user request

assistant → read

toolResult · giant file

Useful once.
Sent again and again.

Save a summary for the next request. Keep the original for when you need it.

Tool calls and their outputs can be large. The extension does not delete the underlying transcript. It captures result batches, makes summaries, indexes originals, then removes only summarized toolResult messages from future model context. Assistant tool-call blocks remain. Note cache trade-off: its default agent-message trigger batches work to avoid constantly changing the prompt prefix.

Two views of the same conversation

The two views begin with the same messages.

This is the most important point about the extension. Click After prune: the stored session still contains original tool results, while the next request copy replaces their detail with a compact summary. The context hook returns a modified messages array; it does not rewrite historical session entries. Click Query t1: the agent calls context_tree_query and receives the indexed original output when it needs it. The query result then joins the ongoing conversation like a normal tool result. 04 / Your first extension

Start with one hook

1

Pick a moment: request, stream, tool, or session.

2

Register one handler or one tool.

3

Try it with pi -e ./extension.ts.

the whole shape

export default function (pi) {
  pi.on("session_start", (_event, ctx) => {
    ctx.ui.notify("Hello!", "info");
  });
}
This is enough to get started: export a function, receive Pi's API, and register a handler. Pi calls it when the event happens. Try pi -e ./extension.ts locally. For automatic loading, put the file in ~/.pi/agent/extensions or the project's .pi/extensions, then /reload. Check the docs for your Pi version when adding imports; package names can differ. The three repositories have full examples. I'd start by watching one event and showing a status message, then add behavior from there.
