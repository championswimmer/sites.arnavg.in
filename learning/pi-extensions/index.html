Stress the distinction between model and harness. The model selects tool calls; the harness owns the actual tools and their results. That means extensions can affect the system without changing model weights or forking core Pi.

02 / Event-driven extension

A hook is a named moment in that loop

Pi emits

event: "tool_call"
toolName: "bash"
input: { command: "npm test" }

An event carries the details available at that moment.

Extension listens

export default function (pi) {
  pi.on("tool_call", (event, ctx) => {
    // inspect, block, or react
  });
}

The default export receives Pi’s extension API. Add one handler; the harness calls it at the boundary.

Hooks can observe events, alter some payloads, or block some actions. The event’s contract decides which.

A Pi extension exports a default function that receives an ExtensionAPI object. Calling pi.on registers a handler. This example uses tool_call, which can inspect a proposed tool and return block=true with a reason. Other hooks have different allowed return values, so never generalize that every hook can modify everything. The snippet is intentionally tiny for a projected slide.

02 / Four ways to extend

Hooks are only one door

pi.on(...)

Event handlers

Observe or shape moments in the lifecycle.

Example: trim future context.

pi.registerTool(...)

Agent tools

Give the model a new callable capability.

Example: update a checklist.

pi.registerCommand(...)

User commands

Offer a slash command to control the feature.

Example: /speed or /pruner.

ctx.ui + pi.appendEntry

UI + state

Show status, widgets, dialogs, and session data.

Example: persistent task view.

Extensions may combine these APIs. pi-context-prune uses event hooks and tools. pi-speedometer uses event hooks, a status UI, and a user command. pi-checklist uses tools, commands, UI, and session persistence. Agent tools are callable by the model; slash commands are initiated by the human.

Case study B / pi-speedometer

“It feels slow” becomes two numbers

TTFT

Request → first content delta

412 ms

TPS

Output tokens ÷ time since first delta

42.1 t/s

Pi footer | ⚡ 42.1 t/s ⏱ 412ms

TTFT means time to first token, implemented as time to first content delta after before_provider_request. TPS is output tokens divided by elapsed seconds since that first delta. Speedometer uses ctx.ui.setStatus; it does not add a model tool. Its UI is useful during a live demo to separate startup latency from generation throughput.

Mutations commit a snapshot with pi.appendEntry and also include it in tool result details. On session_start and session_tree, the extension walks the current branch and takes the last valid snapshot; that makes branching and navigation coherent. 04 / Your first extension

Start with one seam

1

Pick a moment: request, stream, tool, or session.

2

Register one handler or one tool.

3

Try it with pi -e ./extension.ts.

the whole shape

export default function (pi) {
  pi.on("session_start", (_event, ctx) => {
    ctx.ui.notify("Hello!", "info");
  });
}
This is the minimum mental model: default export a function receiving the extension API; register behavior once; Pi loads the module and calls handlers at the named boundary. For a quick local experiment use pi -e path. For auto discovery, put an extension in ~/.pi/agent/extensions or project .pi/extensions, then /reload. The published Pi docs currently describe this, although import package names can vary across Pi versions. The three case-study repos provide complete examples. A good first extension observes one event and paints a status, then grows into mutation or tools only when needed.
