00–05 MIN · THE STORAGE CONTRACT

A disk is just bytes

A filesystem turns numbered blocks into names, objects, and promises.

You already know the interface: open a path, read some bytes, close it. Underneath, an SSD does not know what report.txt means. It exposes logical block addresses. Your filesystem must decide which bytes describe files, which bytes contain their contents, and which space is available for reuse.

Namespace

How does /docs/report.txt identify an object?

Storage

Where are that object's metadata and bytes?

Semantics

What must remain true during sharing, failure, and restart?

Three units that sound alike

A logical sector is a device addressing unit, commonly 512 or 4096 bytes. A filesystem block is a unit your format chooses for allocation and layout. A memory page belongs to virtual memory and caching. These can have the same size, but they are different contracts. Our teaching format chooses 4096-byte filesystem blocks.

On a conventional SSD, the controller translates logical addresses to flash pages and handles wear leveling. On an HDD, the driver and controller handle mechanical placement. Your first filesystem sits above those drivers: on Linux, it reads a block device such as a partition through a file descriptor. Raw NAND and zoned devices need additional rules; this course assumes an ordinary randomly writable block device.

Use a file as your first device

A disk image is a regular file containing your filesystem's exact bytes. Your code reads at block_number × block_size with pread(). Later, the backing descriptor can refer to a partition instead. The image lives on a host filesystem, so it has an extra layer of caching and allocation; it still lets you develop your format without writing a storage driver.

Formatting creates the initial metadata. Mounting connects an existing format to a directory in the OS namespace. Neither is the same as partitioning, which divides a device into address ranges. You can put a filesystem directly on a whole device, but writing its first blocks can destroy an existing partition table.

Your working contract: read bytes at an offset, write bytes at an offset, report errors, and request durable storage. Everything above that—including folders—is your design.

05–13 MIN · IDENTITY & LIFETIME

Names point to inodes

A filename is a directory entry. The file is a different object.

An inode holds a file's identity and metadata within a filesystem: object type, permission bits, owner and group IDs, byte length, link count, timestamps, and a way to find its data. Inode numbers are scoped to a filesystem and can be reused after deletion. Persisting an inode number alone is not a universal file identifier.

A directory is a special file containing a mapping from names to inode numbers. To resolve /docs/report.txt, start with the root inode, find docs in its directory contents, then find report.txt in that directory. An inode typically does not store its own filename; multiple names can refer to it.

Hard links, symbolic links, and renames

A hard link adds another directory entry for the same inode. It increments that inode's link count and shares the same contents and metadata. Ordinary hard links do not cross filesystem boundaries, and directory hard links are generally forbidden to avoid cycles.

A symbolic link is its own object containing a path string. Resolution follows that string unless the operation says otherwise. It can cross mounts and can dangle when its target disappears. A relative symlink is resolved relative to the directory containing the link.

A same-filesystem rename changes the namespace; it need not move file data blocks. Open handles continue to identify their objects. Cross-filesystem renames fail with EXDEV; tools such as mv may then copy and delete. Atomic visibility of a rename does not by itself promise persistence after power loss.

Unlink is a lifetime operation

unlink() removes a directory entry and reduces the link count. If there are no names but an open reference remains, existing reads and writes can continue. Reclaim the inode and blocks only after there are no remaining links or live references requiring the object. Memory mappings also matter. A crash loses process references; a writable filesystem needs a recovery policy for such orphaned objects.

Metadata is behavior

For a regular file, read permission allows reading bytes; write permission allows changing contents. For a directory, read allows listing names, execute allows searching/traversing, and write allows modifying entries subject to other checks. Deleting a file is primarily governed by its parent directory's permissions, including sticky-bit rules—not by whether the file itself is writable.

mtime tracks content modification; ctime tracks inode-status change, not creation. atime concerns access and may be relaxed by mount policy. Creation time, when available, is separate. A Linux VFS inode in memory need not have the same representation as your serialized inode on disk.

13–21 MIN · THE PROCESS VIEW

Descriptors are not files

Separate the per-process handle from the shared open state.

A file descriptor is a small integer in a process's descriptor table. Entries 0, 1, and 2 conventionally represent standard input, output, and error. A descriptor can also refer to a pipe, socket, or device; it does not imply a disk file.

An open file description is the kernel object created by an open(). It records the current offset and file status flags. A descriptor points to that object, which refers to the underlying file. Two independent opens of the same inode usually produce different open file descriptions. dup() creates another descriptor pointing to the same open file description.

EXPERIMENT 03Who moved my offset?

File contents: ABCDEFGHIJKL. FD 3 and FD 4 were created by open() and dup(3). FD 5 came from a second open().

Predict the next three bytes before each click.

Follow a short program

C · RETURN CHECKS OMITTED FOR EXPLANATION
int a = open("notes.txt", O_RDONLY); // assume a == 3
int b = dup(a);                     // b == 4, same open description
int c = open("notes.txt", O_RDONLY);// c == 5, independent offset
read(a, buf, 3);                    // ABC; shared offset becomes 3
read(b, buf, 3);                    // DEF; shared offset becomes 6
read(c, buf, 3);                    // ABC; c's offset becomes 3
pread(b, buf, 3, 0);                // ABC; shared offset stays 6

fork() copies descriptor references into the child; corresponding descriptors still share open file descriptions. lseek() changes that shared offset. pread() supplies an explicit position without changing it, which is useful when many filesystem requests read the same backing device. Descriptor flags such as close-on-exec belong to descriptor entries; status flags such as append belong to the open description.

Your FUSE daemon has its own handles

There are three different identifiers to keep straight: the application's FD, the daemon's FD for its backing image/device, and fi->fh, a value your FUSE callback can set to identify a daemon-side open handle. They are not interchangeable. The kernel does not ask you to assign the application an FD. It manages that table itself.

The read callback receives a requested offset and size. Use those parameters; do not maintain one global cursor for the file. A writable implementation should resolve a name at open time, retain an inode reference in an open-handle table, and use that reference for later I/O even after a rename or unlink.

Predict: two threads call lseek() then read() on a shared descriptor. Another seek can interleave between those calls. An explicit-offset pread() avoids that particular race; it does not make concurrent writes to file contents disappear.

21–28 MIN · THE ON-DISK FORMAT

Design the bytes on disk

A filesystem format is a durable data structure with invariants.

Meet TinyFS, our deliberately small format: a 16 MiB image, 4096-byte blocks, 128 inode slots, and 12 direct block pointers per inode. It supports a root directory and a read-only file in the runnable starter. The writable design later in the course extends these same pieces. This is our format, not ext4.

Find a byte inside a file

File byte offset x gives logical block x / 4096 (integer division) and offset x % 4096. Read the corresponding inode pointer to obtain a physical filesystem block. The device address becomes pointer × 4096 + within_block_offset. Logical file blocks can map to nonadjacent physical blocks.

EXPERIMENT 04Translate a file read

Example inode pointers: [8, 14, 9, 0]. Zero is a sparse hole, not a pointer to the superblock. File size is 16 KiB.

What the limits cost you

Twelve direct pointers cap one file at 12 × 4096 = 49,152 bytes. An indirect block can hold additional pointers; a tree scales further. An extent records a run such as “logical blocks 0–99 live at physical blocks 800–899,” reducing metadata for contiguous files. These are alternate mapping designs, not required ingredients for a first mount.

Allocation rounds physical storage to blocks. A non-sparse 5000-byte file needs two blocks and leaves 3192 bytes unused at the end. A sparse file can have a large logical length with few allocated blocks; reads from holes return zeros. On Linux, st_size is a byte length, while st_blocks counts allocated storage in 512-byte units.

Serialize explicitly

Use fixed-width fields and a specified byte order. Do not write a C struct directly: compiler padding, alignment, and endianness vary. Our superblock begins with eight magic bytes TINYFS1\0, then little-endian 32-bit version, block size, and block count at offsets 8, 12, and 16. The inode table begins at byte 12,288; inode i starts at 12,288 + i × 128.

28–36 MIN · THE OS ADAPTER

Put FUSE in the middle

FUSE exposes your implementation to ordinary applications.

FUSE means Filesystem in Userspace. On Linux, the kernel's FUSE driver forwards filesystem requests to a userspace daemon through /dev/fuse. libfuse manages the protocol and calls your functions. The daemon can read a local disk format, talk to a remote service, or synthesize data; FUSE itself does not define an on-disk format.

EXPERIMENT 05Trace a cold read

Walk through one illustrative, uncached request. Real syscall-to-callback traffic depends on lookup and data caches.

Two APIs, one filesystem

The high-level API gives callbacks such as getattr(path) and read(path, …, fi). It handles much of the name-to-node bookkeeping. The low-level API uses node IDs, explicit replies, lookup reference counts, and forget notifications. It offers more control but requires you to manage those lifetimes correctly. We start with the high-level libfuse3 API.

OperationYour job
getattrFill struct stat with type, mode, size, links, and ownership

Small contracts that cause large bugs

libfuse high-level callbacks return negative errno values on error: -ENOENT for a missing name, -EIO for failed/corrupt storage access, -ENOSPC for no free space. A read normally fills the requested region except at EOF or on error; short replies in cached mode can be padded with zeros. Do not silently turn an unexpected short backing-device read into a successful file read.

A FUSE read request is not necessarily one application read. The kernel may satisfy reads from page cache, fetch ahead, or combine work. Metadata has cache lifetimes too. Choose a conservative cache policy first, make the daemon the sole modifier of its backing storage, then measure. Turning on writeback caching changes responsibilities around append and may produce read requests for write-only opens.

flush is not fsync. It can occur multiple times for one open, including when duplicated descriptors close. release concerns handle lifetime; it is not a reliable place to report durability errors. Your backend also has a descriptor, so there may be a FUSE cache, daemon buffers, the host page cache, and the device's own cache between a write and persistent media.

Scope: the Unix ideas carry across systems. The runnable commands use Linux and libfuse3. macOS requires its own FUSE implementation and platform setup; this is not a single portable binary for every Unix.

36–48 MIN · THE BUILD LAB

Mount your first filesystem

Format an image, parse its metadata, and serve its bytes through FUSE.

The included starter is an actual read-only disk-format reader. It loads the superblock, bitmaps, inode table, root directory, and file data from the image. The file contents are not hardcoded in the FUSE callback. You can read the whole implementation here and download it without leaving this page.

Use Linux with FUSE enabled, a C compiler, Python 3, and libfuse3 development headers. A VM works well. Containers need explicit host support for FUSE. Browser experiments need none of this. Allow extra time beyond the hour if you need to provision a Linux environment.

1. Create a fresh image

Save both downloads in a new working directory. On Debian or Ubuntu, install the packages below. The formatter creates only a new regular file using exclusive creation; it refuses to overwrite an existing path and does not format block devices.

LINUX SHELL
sudo apt update
sudo apt install build-essential pkg-config libfuse3-dev fuse3 python3
python3 make_image.py tiny.img
od -Ax -tx1 -N 32 tiny.img

You should see the magic bytes 54 49 4e 59 46 53 31 00. The formatter marks blocks 0–8 allocated, reserves inode 0, initializes root inode 1 pointing to directory block 7, and writes inode 2 pointing to file block 8. A format operation establishes every invariant needed for the first lookup.

2. Compile and mount

LINUX SHELL · TERMINAL A
cc -std=c11 -Wall -Wextra -O2 tinyfs.c -o tinyfs $(pkg-config fuse3 --cflags --libs)
mkdir mnt
./tinyfs tiny.img mnt -f -s

-f keeps the daemon in the foreground; -s selects single-threaded request handling. The program supplies ro,default_permissions: the mount is read-only and the kernel checks Unix permission bits from your attributes. The image is opened before libfuse starts, so daemonization would not change the backing file being used.

3. Prove it is reading your format

LINUX SHELL · TERMINAL B
ls -l mnt
cat mnt/hello.txt
# Expected first line: Hello from TinyFS!
python3 - <<'CHECK'
import os
fd = os.open('mnt/hello.txt', os.O_RDONLY)
assert os.pread(fd, 5, 0) == b'Hello'
assert os.pread(fd, 5, 10**6) == b''  # EOF
os.close(fd)
print('offset and EOF checks passed')
CHECK
fusermount3 -u mnt

Mount again with the same image and repeat cat. This establishes that bytes and metadata survive a daemon restart. Try a nonexistent path and a write: the first should fail with a missing-file error; the second with a read-only-filesystem error. Do not edit the backing image while it is mounted.

4. Read the code in the order requests need it

  1. open_image() checks device/image size, magic, and geometry, then loads the bitmaps.
  2. lookup() scans the root directory's stored entries to obtain an inode number.
  3. load_inode() decodes little-endian fields and bounds-checks the size and pointers.
  4. tiny_open() stores that inode number in fi->fh. This simple immutable format needs no allocated per-open object.
  5. read_inode() splits a read at block boundaries, clamps it at EOF, and fills sparse holes with zeros.

5. Replace the image with hardware

The filesystem logic still uses byte offsets. A Linux partition device makes offset zero relative to the start of that partition, so you must not add the partition start again. If you choose an entire disk instead, your format owns that disk's address space, including where a partition table might otherwise live.

Use a disposable device or spare partition that contains nothing you need. Identify it by model, size, serial, and a stable /dev/disk/by-id/… path. Unmount it and ensure it is not swap, part of a mounted parent device, or used by another storage stack. Formatting or copying an image to the wrong target destroys its existing bytes.

sudo blockdev --getsize64 /dev/disk/by-id/VERIFIED-SPARE-PARTITION
sudo blockdev --getss /dev/disk/by-id/VERIFIED-SPARE-PARTITION

For the first hardware milestone, an explicit device-formatting tool would open that verified partition exclusively, check capacity (at least 16 MiB), then write the exact TinyFS image bytes starting at partition offset zero and sync the device. The included formatter intentionally only creates images; the hardware write is a separate, destructive step. No existing ext4/FAT filesystem should be mounted on that partition at the same time.

After the format has been placed there, pass the verified device path in place of tiny.img to the daemon. The C starter supports regular images and Linux block devices, queries block capacity with BLKGETSIZE64, and requests exclusive block-device access. It uses buffered I/O; a filesystem block is not a claim of atomic hardware writes. What this starter does not implement: writes, nested directories, links, timestamps, journaling, or comprehensive hostile-image validation. Storage-reader checks can run with cc -DTINYFS_CHECK tinyfs.c -o tinycheck and ./tinycheck tiny.img. Full mounting requires a Linux FUSE environment.

48–55 MIN · CONSISTENCY & DURABILITY

Make writes survive failure

A successful write, a consistent format, and durable data are different promises.

Implement a write before optimizing it

For an overwrite within existing blocks, preserve bytes outside the requested region. For growth, reserve free blocks, zero newly exposed gaps, write the new data, and update the inode's mapping and size. A file read must never expose old bytes from a previous owner's block. For shrink, adjust the size and free blocks no longer referenced; zero the truncated tail before it can be exposed again by later growth.

PSEUDOCODE
write(handle, bytes, offset):
    lock inode and allocator in a fixed order
    validate offset, overflow, and the 48 KiB file limit
    reserve needed blocks; fail cleanly if there is no space
    prepare zeroed new blocks; preserve unchanged bytes
    update data, block bitmap, inode pointers, size, timestamps
    commit according to the filesystem's recovery protocol
    release locks; return bytes written or a specific error

This is an algorithm outline, not a crash-safe implementation. You need rollback or transaction handling when allocation, I/O, or metadata updates fail. ENOSPC can mean no free blocks or no free inode slots. A first writable version can serialize all mutations with one lock; later, introduce finer locks with a fixed acquisition order. pread() avoids a seek race, not allocation races.

Crash in the middle of creating a file

A create changes data blocks, an inode, allocation metadata, and a parent directory. A crash can interrupt that multi-block change. Explore a simplified transaction below: each step is assumed durable before the next. Real devices can reorder or tear writes, so a real journal needs ordering, validation, and replay rules beyond this model.

EXPERIMENT 06Pull the plug

Compare both designs after step 2 and step 4. When is replay allowed?

Journal, copy-on-write, or repair?

A redo journal records intended metadata updates, makes the log durable, then makes a commit record durable. Recovery replays committed transactions and ignores incomplete ones. Home-location updates can follow; reclaim log space only after checkpointing is durable. Ordering file data before metadata commits can prevent a new name from exposing unwritten contents. Metadata journaling alone does not preserve every file-data overwrite.

Copy-on-write builds updated blocks elsewhere and publishes a new root after dependencies are durable. It still needs a reliable root selection scheme, checksums/generations, and safe space reclamation. fsck scans the format for broken invariants; it can reclaim leaks or detect duplicate ownership, but it cannot reconstruct arbitrary lost application data.

What should fsync mean?

A returned write() may only mean bytes were accepted into memory. Your FUSE fsync must finish relevant daemon work, make the necessary file data and metadata recoverable, and sync the backing descriptor while reporting failures. fdatasync may omit metadata irrelevant to retrieving the data; file size is still necessary. For an application that creates or renames a file, persisting the parent directory may require a separate directory sync.

PSEUDOCODE
# Application-level durable replacement pattern (conceptual)
write complete contents to a temporary file in the same directory
fsync(temporary_file)
rename(temporary_name, final_name)
fsync(parent_directory)

Support fsyncdir for that last promise. Device flushes only help when the underlying storage honors them; a “4096-byte block” does not imply a power-failure-atomic 4096-byte write. Test interruption at each update boundary, then validate the image after restart.

55–60 MIN · CHECK YOUR MENTAL MODEL

Your filesystem build plan

You now have a storage format, an OS adapter, and a path to a writable filesystem.

Spend the last five minutes checking that you can predict behavior, not just recognize terms. The questions can be retried. Each answer explains the underlying rule.

Build in milestones you can prove

The invariants your checker should enforce

  • Every inode and data reference is in range and points to allocated storage.
  • Each allocated data block has the intended owner; accidental aliases are corruption.
  • Directory records are well formed and reachable objects have the expected link counts.
  • File size is representable by its mapping; holes are deliberate and return zeros.
  • Unreachable allocated objects are either recognized orphans or leaks to repair.
  • A completed sync remains recoverable after restart according to your documented guarantees.

Choose the next complexity deliberately

Add statfs so df can report space. Add ownership, timestamps, and permission changes for normal Unix tools. Expand the directory model before adding an index. Introduce indirect blocks or extents when the 48 KiB limit becomes the thing you want to learn next. Only then tune caches, batch metadata writes, or optimize the allocator.

Checksums help detect corruption; they do not supply repair data by themselves. Journaling helps recovery; it is not a backup. Replication can preserve the same logical mistake on every copy. Keep those promises separate as the design grows.

Final challenge

Explain, without looking back, what changes on disk and in memory when a process opens a file, duplicates its descriptor, unlinks its name, reads through the duplicate, and closes both descriptors.

Compare your explanation

Open resolves the directory name to an inode and establishes an open file description plus an FD. Dup adds another FD referencing that same open state. Unlink removes the name and decrements the inode's link count. The open reference preserves access, and both descriptors share the file offset. Closing one FD leaves the other usable. After the final live reference is gone, an inode with zero links and its blocks can be reclaimed. A writable implementation must also handle a crash before orphan cleanup finishes.
